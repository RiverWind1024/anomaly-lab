# 平台垂直切片

把「数据源 → 指标 → 告警任务 → 定时执行 → 基线预览」串成一条可运行的链路，对应 [my-thought.md](my-thought.md) 里第一阶段的设想。

## 快速体验

```bash
make platform-demo          # 生成 demo 源库 + 指标 + 任务（写入 data/）
make serve                  # 构建前端并起服务：http://127.0.0.1:8000/
```

页面（前端路由）：

信息架构是 **数据源 → 指标 → 序列** 三级从属 —— 先有数据源，在数据源上配指标，
指标被告警任务跑出序列。

侧边栏把「数据源」与「指标」收进一个 **「数据」分组** ——
两者是从属关系，平铺成两个一级入口会丢掉这层。
序列仍靠页面内下钻（它是跑出来的结果，不是配置项）。

| 路径 | 内容 |
|---|---|
| `/` | 概览（数据源→指标→任务→告警→运行→反馈的全貌，一次请求拿全） |
| `/sources` | 数据源列表（各源有几个指标一目了然） |
| `/sources/:id` | 数据源详情：它的指标列表 + 用它的任务 |
| `/metrics` | 指标列表（所有指标 + 所属数据源 + 取数配置） |
| `/metrics/new?source_id=` | **新增指标**（独立页面，不是弹窗） |
| `/metrics/:id/edit` | **编辑指标**（与新增同一条路径） |
| `/metrics/:id` | 指标详情：配置 + 用它的任务 + 各任务最近跑出的序列 |
| `/metrics/preview` | **指标预览**（选数据源 + 选指标 → 看它的时序图与明细） |
| `/metric-preview` | 指标取数浏览器（写只读 SQL 看结果；**顶部有 Grafana 风格时序图**；**可切数据源**） |
| `/jobs` | **告警任务**列表 + 新建任务（含告警规则录入） |
| `/jobs/:id` | 任务**配置**（改参数、看告警规则） |
| `/jobs/:id/test` | **测试告警**（真跑一次但不落库 —— 见下） |
| `/jobs/:id/runs` | 运行记录（序列数 / 告警数 / 耗时 / 错误） |
| `/jobs/:id/detections` | 检测结果（预览图 + 多算法对比 + 分类结论） |
| `/jobs/:id/feedback` | 人工反馈与调参建议 |
| `/alerts` | **告警记录**（跨任务汇总；按任务/等级/序列/时间筛选，详情看图） |
| `/evaluation` | 评估报告（筛选 + 维度聚合 + 删除检测记录） |
| `/detections` | 检测记录（筛选 + 分页；某条序列的一次检测：数值/分数/阈值 + 误报漏报区间） |
| `/annotate` | 标注（刷选 + 类型下拉） |

旧 URL 兼容：`/badcases` → `/detections`、`/platform` → `/jobs`。

### 侧边栏的两组从属关系

```
概览
数据 ├ 数据源
     └ 指标          ← 指标从某个数据源取数
告警 ├ 告警任务      ← 定时跑检测的任务
     └ 告警记录      ← 跑出来的告警事件
评估报告
检测记录
标注
```

⚠️ **「告警记录」与「检测记录」不是一回事**：
前者是**有告警的事件**（跨任务汇总），后者是**每次运行里每条序列 × 算法的检测明细**
（没告警的序列也在里面）。

⚠️ 侧边栏的**告警数徽标挂在「告警记录」上** —— 它是一个待处理的队列。

### 为什么新增/编辑指标是独立页面而不是弹窗

指标配置要**写 SQL、要选列、要预览取回来的数据** ——
弹窗塞不下这些；预览要开新标签页时，弹窗会跟着一起消失。
独立页面能给「预览数据」腾出位置。

新增与编辑**共用同一套表单代码**（`/metrics/new` 与 `/metrics/:id/edit`），
两者不会走偏。

### 测试告警：真跑一次，但不落库

`POST /api/platform/jobs/{id}/test-run` 与「立即运行」的区别**只有两处**：
不写 `runs` 表、不写结果文件。取数、检测器选择、打分、分级**全都走同一段代码**
（`runner._compute_job`）—— 所以试跑看到的就是真跑会得到的。

⚠️ 告警点**逐个列出、不抽样** —— 抽样可能正好丢掉告警点，
用户会误以为「没有告警」。

开发时前后端分开跑（vite 热更新 + `/api` 代理）：

```bash
make dev                    # vite :5173（代理 /api → :8000） + uvicorn :8000
```

带假远端（见下文「假远端时序数据库」）一起跑：

```bash
MOCK_TSDB=1 make dev        # 上面两个 + 假远端 :8181
```

或者纯脚本冒烟（不启 Web）：

```bash
make platform-smoke         # 跑一次任务并断言：2 条序列、有告警
```

## Web 前端

前端是 `frontend/` 下的**独立工程**（React 18 + TypeScript + Vite + Ant Design v5 +
TanStack Query + ECharts），后端只提供 JSON API 并托管构建产物。

- **工程结构**：`src/api/`（端点封装 + 手写类型 + 契约守卫）、`src/components/`（五态边界、
  布局）、`src/features/<领域>/`（页面实现与单测）、`src/styles/tokens.css`（唯一视觉来源）、
  `src/theme/`（AntD token、ECharts 的 CSS 变量读取、主题上下文）。
- **五态处理**：统一走 `StateBoundary` —— 加载 / 空 / 错误 / **数据不足** / 正常。
  数据不足是业务态而非错误态：后端用 `X-Anomaly-Biz-State` 响应头（`no_run`、`no_series`、
  `no_data`、`insufficient_data`、`no_algorithms`、`no_result`）标记，前端显示空态或警告，
  不会出现红色错误框。旧版的 `alert()` / `prompt()` 全部消除（标注类型改下拉）。
- **单一视觉来源**：颜色只定义在 `tokens.css` 的 CSS 变量里，AntD 通过 `ConfigProvider` token、
  ECharts 通过 `theme/cssVar.ts` 运行时读取，两套主题（`data-theme=dark|light`）共用同一份变量。
  ECharts 不会因 CSS 变量变化自动重绘，图表组件订阅主题上下文来重绘。
- **类型防漂移**：`src/api/types.ts` 手写（决策 D6），后端字段一变
  `tests/web/test_api_contract.py` 就会红。
- **构建与托管**：`make frontend-build` 产出 `frontend/dist`（不入 git）；`serve` 依赖它，
  FastAPI 对非 `/api/*` 路径回 `index.html`（深链接不 404），`/assets` 静态挂载。

## 三层配置模型

| 概念 | 存哪 | 关键字段 |
|---|---|---|
| 数据源 Source | `data/platform.db` 的 `sources` | 名称、类型（`sqlite` / `http`）、路径（SQLite 源用：相对数据根目录或绝对路径）、类型专属配置（`config` JSON） |
| 指标 Metric | `metrics` | 数据源、SQL、时间列、值列、分组列、时间格式、源时区、缺失值策略、采样频率 |
| 告警任务 Job | `jobs` | 指标、算法（可填 `auto`）、告警规则表、窗口点数、执行间隔、启用状态 |

运行记录在 `runs`，人工反馈在 `feedback`。

⚠️ **检测记录也落库**（两张表）：

| 表 | 内容 |
|---|---|
| `run_series` | 每次运行 × 每条序列的摘要 —— `n_alerts` / `detector` / `metric_class` / `content_hash` |
| `alert_events` | 每次运行报出的**告警区间** —— `level` / `start_ts` / `end_ts` / `n_points` / `max_score` |

⚠️ **但逐点数组仍在文件里**：`data/cache/platform/runs/<run_id>/`
（`index.json` + 每条序列一个 npz）—— 那是图表回放与评估反算的原材料，
350MB 塞进数据库没有好处。

## 时间语义：不猜，必须声明

时间列的存储形式与时区是**数据源的属性**，平台不做猜测（对应 CloudWatch 的 `MetricTimezone`）：

| `time_format` | 含义 | 例子 |
|---|---|---|
| `iso_utc` | ISO8601，自带时区或本身就是 UTC | `2026-01-01T12:00:00+08:00`、`2026-01-01T12:00:00Z` |
| `iso_naive` | 无时区墙钟时间，按 `source_timezone` 解释 | `2026-01-01 20:00:00` + `source_timezone=Asia/Shanghai` |
| `epoch_s` / `epoch_ms` | Unix 时间戳 | `1767268800` |

比较用 SQLite 内置的 `julianday()` 归一化，避开 ISO 字符串字典序比较的坑；`iso_naive` 会把查询边界换算成源时区的墙钟再比。HTTP 数据源没有 `julianday()`，边界改用按 `time_format` 生成的字面量 —— **方言由各自的连接器渲染**（见下节）。

**声明错了的后果**：取不到数据 → 该序列标记为「数据不足」，而不是悄悄取错区间。

## 缺失值：自动兜底 + 可覆盖 + 绝不静默

| `missing_policy` | 行为 |
|---|---|
| `drop`（默认） | 丢弃缺失点，并记录丢弃了多少个 |
| `interpolate` | 按时间线性插值（适合采集抖动造成的空洞） |
| `error` | 严格模式：有缺失就判任务失败 |

**关键**：不管哪种策略，有效点少于 10 个的序列会被标记为 **数据不足（`insufficient_data`）**——既不算异常，也**绝不显示成「一切正常」**。这一条是硬约束：检测没跑起来不能长得像没异常。

## `$timefilter` 与 group by

指标 SQL 里必须**恰好有一个** `$timefilter`，执行时会被替换成时间条件：

```sql
SELECT ts, host, value FROM metrics WHERE $timefilter ORDER BY ts
```

执行时等价于（列名来自配置，已做标识符校验）：

```sql
SELECT * FROM (SELECT ts, host, value FROM metrics
               WHERE "ts" >= ? AND "ts" < ? ORDER BY ts) LIMIT 100001
```

- 时间范围用参数绑定，不做字符串拼接。
- 只允许 `SELECT` / `WITH` 开头的单条语句；含写操作关键字直接拒绝，连接以 `mode=ro` 打开。
- `group_column` 非空时，**在加载层就拆成独立序列**：序列 ID 为 `{指标名}:{分组值}`，检测器永远只面对一条序列。
- 单次查询上限 10 万行，超出要求缩小窗口或加聚合。

时间范围用参数绑定，时间列用 `julianday()` 比较（见上节）—— 这是 **SQLite 源**的说法，HTTP 源走另一套方言。

> ⚠️ **`$timefilter` 的替换由连接器各自渲染** —— 用户在指标里写的 `$timefilter` 不变，
> 展开成什么由数据源类型决定：
>
> | 连接器 | 展开成 | 方式 |
> |---|---|---|
> | SQLite | `julianday("col") >= julianday(?) AND julianday("col") < julianday(?)` | **参数绑定** |
> | HTTP | `"col" >= '<字面量>' AND "col" < '<字面量>'` | 字面量（列名过标识符校验，字面量由平台生成，无注入面） |
>
> HTTP 侧的 `iso_utc` 字面量是 **T 分隔 + `+00:00`**（与平台的 `to_iso()` 完全一致）：
> 同一偏移、同一 ISO 格式下**字符串字典序 == 时间序**，边界比较才正确。
> 用 `Z` 会让 `'+'`(0x2B) < `'Z'`(0x5A) → **边界行被误判**。
>
> 浏览预览与指标运行时走的是**同一个连接器的同一条渲染路径**，所以「预览看到的」
> 必然等于「跑出来的」。

### SELECT 里哪一列是「检测的值」？—— 不是约定，是配置

⚠️ **平台没有任何「叫 `value` 的列就是检测值」的约定。**
指标里存着三个**显式的列名**：

| 字段 | 作用 | 取不到时 |
|---|---|---|
| `time_column` | 时间列 —— 时间条件渲染到它上面 | `查询结果缺少 time_column` |
| `value_column` | **检测的值** —— 送进检测器的就是这一列 | `查询结果缺少 value_column` |
| `group_column` | 分组列 —— 非空时在加载层拆成多条独立序列 | `查询结果缺少 group_column` |

所以 `SELECT ts, series, value FROM metrics WHERE $timefilter ORDER BY ts` 里
送进检测器的是 **`value` 列 —— 因为指标是这么配的**，
换成 `SELECT ts, series, latency FROM ...` 就得把 `value_column` 改成 `latency`。
取列的代码在 `platform/sources/base.py:series_from_frame()`，按名字取，不猜。

**只有「数据浏览器」在写 SQL 的过程中做推断**（为了让用户少填几个框）：

| 列的样子 | 推断成 |
|---|---|
| 列名精确匹配 `ts` / `time` / `timestamp` / `datetime` / `date` / `observed_at` / `observedat` / `event_time` | 时间列（**名字优先于类型**） |
| 类型是 `TIMESTAMP` | 时间列 |
| 类型是 `REAL` / `INTEGER` | 值列 |
| 其余 | 不推断（不作为任何角色） |

⚠️ **名字优先于类型** —— epoch 存的时间列是 `INTEGER`，
只看类型的话它会被判成「值列」：`ts` 抢走了值列的角色、
真正的 `value` 反而「不使用」，**完全反了**。
⚠️ **两个数值列时，列顺序里第一个被当成值列** —— 靠列顺序猜，
在列头的角色下拉里改。
⚠️ 推断只影响**浏览 → 建指标**这一步；指标一旦存下来，
`value_column` 就是死的，不会再变。

### `$timefilter` 需要知道时间列 —— 所以浏览时有个先后顺序

`$timefilter` **不是 SQL**，是平台的占位符 —— 它要渲染成
「**某一列**上的时间条件」，所以平台必须先知道是哪一列。
浏览时还没指定时间列就用 `$timefilter`，请求会被拒（400）。

⚠️ 这里有个**先有鸡还是先有蛋**：用户正是靠这条 SQL 才知道结果里有哪些列的。
绕法：**先去掉 `$timefilter` 跑一次**（浏览器的默认语句就是不带它的
`SELECT * FROM metrics LIMIT 100`），看到列以后再把时间列填上。

## HTTP 数据源（SQL 透传）

平台支持把指标 SQL **原样发给远端 SQL-over-HTTP 网关**：远端自己执行、只返回结果集，
平台不落地也不代算。常见端点：

| 网关 | 端点 |
|---|---|
| InfluxDB 3 / Cloud Serverless / Dedicated | `POST /api/v3/query_sql` |
| ClickHouse | `POST /?query=` |
| TDengine | `POST /rest/sql` |

> ⚠️ 支持的是「**SQL-over-HTTP 网关**」这个形态，**不是**某个具体产品 ——
> 能不能连上取决于那个网关本身（路径、参数名、鉴权方式、响应格式）。

### 配置字段

`sources` 表新增 `config` JSON 列存类型专属参数；HTTP 源的参数全在这里：

| 字段 | 必填 | 语义 |
|---|---|---|
| `url` | 非空 config 时 | URL 模板，`{sql}` 占位符在此生效（空 config 允许「先建后配」） |
| `method` | | `GET`（默认）/ `POST` |
| `body` | | body 模板（JSON 对象）；`{sql}` 占位符在此生效 |
| `headers` | | 原样发送的请求头（如 `Authorization`） |
| `format` | | `json`（默认）/ `csv` / `jsonl` |
| `rows_path` | | 点号路径，指向响应里那个「对象数组」 |
| `timeout_seconds` | | 默认 30 |

`kind` 已收敛为枚举（`sqlite` / `http`），建/改数据源时校验。

⚠️ `headers` / `body` 必须是**对象** —— 传字符串的话脱敏会整段跳过（明文密钥
直接出现在 API 响应里），而且取数时 `.items()` 会抛 `AttributeError`。建/改数据源
时当场拒绝（400）。

### `{sql}` 占位符：URL 里编码，body 里原样

- **URL 里做 URL 编码** —— SQL 里的空格、`#`、`&` 会直接破坏 query string。
- **body 里原样替换** —— 百分号编码会污染 SQL 本身（`'` 变成 `%27` 之类，远端就认不出了）。

### `format`：请求与响应对齐

`format` 一个字段管两端：**请求侧的格式参数**写在 `body` 模板里，
**响应侧**由平台按 `format` 决定怎么解析：

| `format` | 响应怎么解析 |
|---|---|
| `json` | JSON 对象数组（数组位置可用 `rows_path` 指定） |
| `csv` | CSV，**必须带表头行**（InfluxDB 的 csv format 带头；ClickHouse 的 `FORMAT CSVWithNames` 带头） |
| `jsonl` | 每行一个 JSON 对象 |

⚠️ **请求的格式与解析的格式必须一致**：平台按配置里的 `format` 解析响应，
远端按请求里的 `format` 返回。body 模板里**没写** `"format"` 时，平台会注入
配置里的那个；写了但与配置不一致 → **当场报错**（否则平台会用 JSON 去解析
一段 CSV，报错还会指向完全无关的地方）。

### `rows_path` 的明确限制

只支持**单层点号路径**指向**一个对象数组**（如 `"data"` / `"results.items"`）。

⚠️ **不支持** InfluxDB 3 的两段式响应（`results[].series[].columns` + `values`）——
那不是一个「对象数组」，`rows_path` 够不着。**接 InfluxDB 3 请用 `format=csv`。**

### 安全边界：远端账号的权限

⚠️ **SQL 原样发到远端执行。** 平台侧的只读校验（`SELECT`/`WITH` 开头、单语句、
写关键字黑名单）只是**第二道防线** —— 关键字黑名单**可以绕过**。

真正的边界是**远端账号的权限**：必须用**只读凭据**（只授 `SELECT` 的数据库账号）。
拿能写的账号配进来，等于把写权限交出去了。

### 凭据脱敏

`headers` 的值**一律脱敏**（`Bearer ••••` / `••••`），`body` 里键名含
`token`/`key`/`password`/`secret` 的值脱敏（**递归** —— 嵌套 dict / list 里的
凭据键也脱），`url` query 里的同类参数也脱敏，**`url` 里的 userinfo
（`user:pass@host`）也脱** —— 脱敏在 **store 层**做，返回给前端的都是脱敏值。

回写时若新值仍等于脱敏形式，则**沿用旧的真值**，不会把密钥冲成 `••••`。
⚠️ 但**认不出对应旧 key** 时（用户把 `token` 改名成 `access_token`，表单里
显示的还是 `••••`）会**当场报错**（400）—— 哨兵值存下去远端就收到字面量
`••••`，源直接坏掉，界面上却看不出区别。

⚠️ URL 的脱敏与还原都是**文本级**的 —— 不重新编码整个 query，
否则 `{sql}` 会变成 `%7Bsql%7D`，模板就废了。

## 数据浏览器

在数据源上写一段**只读 SQL** → 看列结构与前 N 行 → 一键生成指标。

```
POST /api/platform/sources/{id}/query
  body: { "sql": "SELECT ts, host, value FROM metrics WHERE $timefilter",
          "start": "2026-10-30T00:00:00Z", "end": "2026-10-31T00:00:00Z",
          "limit": 100,
          "time_column": "ts", "time_format": "iso_utc", "source_timezone": "UTC" }
  resp: { "columns": [{"name": "ts", "type": "TIMESTAMP"}],
          "rows": [[...]], "time_values": [1793328000000, ...],
          "total": 100, "truncated": true, "elapsed_ms": 12 }
```

⚠️ 还可以给 `freq` + `window_points` —— **时间范围由平台算**：

```
  body: { "sql": "SELECT ts, value FROM t WHERE $timefilter",
          "freq": "1min", "window_points": 60, ... }
```

范围 = `now - freq_delta(freq) × window_points` ——
与**指标运行时同一段代码**（`runner.py` 里也是这个式子）。
前端自己算会漂移，那样「预览看到的」就不是「跑出来的」。
显式给了 `start`/`end` 时以显式的为准。

- `columns[].type` 由 pandas dtype 推断：`TIMESTAMP` / `INTEGER` / `REAL` / `TEXT`。
- ⚠️ `limit` **下推**到发出去的 SQL（`SELECT * FROM (...) LIMIT n`）——
  否则整个结果集会被拉进内存。平台实际多取一行用来判断「还有更多」。
- `total` 是**本次取到的行数**（≤ `limit`），**不是**结果集的真实总行数 ——
  `limit` 已下推，平台根本没看到更多的行。
- `truncated` 表示**还有更多行**（本次取到的行数已经撞到 `limit`）。
- `time_values` 是**时间列解析成的 epoch 毫秒**（前端画时序图用）——
  详见下面「时序图：时间轴坐标由后端算」。
- **检测取数不受 `limit` 影响**（它走指标运行时那条路径）。
- 不落库、不建指标 —— 只是让用户在定指标前先看到「查出来到底是什么结构」。

### 两套占位符，职责清晰

| 占位符 | 用于 | 语义 |
|---|---|---|
| `$timefilter` | 指标 SQL，**浏览也可用** | 平台知道时间列与格式，替换成完整的时间条件 |
| `{start}` / `{end}` | 浏览 SQL | 用户自己在 SQL 里写列名，平台只替换成时间字面量 |

- 浏览 SQL 里含 `$timefilter` 时，需要额外给 `time_column`（`time_format` /
  `source_timezone` 缺省为 `iso_utc` / `UTC`）；**时间条件由连接器渲染** →
  浏览预览与指标运行时结果一致。
- ⚠️ **浏览时可以不写 `$timefilter`，自己写时间条件也行** ——
  浏览只要求「只读 + 单语句」，时间条件随你写。
  但 **指标里必须恰好有一个**（`validate_query` 强制）：指标是**滚动窗口**执行的
  ——调度器每次按 `now - freq × window_points` 取一个窗口，
  `$timefilter` 就是那个窗口的边界。写死时间条件 = 窗口永远不滚动，
  数据会一直是旧的。
- ⚠️ **自己写时间条件时，日期选择器完全不生效** —— 它只替换 `$timefilter`。
  界面会提示这一点（静默失效最让人懵）。
- ⚠️ 浏览的明细列表**分页**（单页 20 行）—— 一次取 100 行，全摊开是一屏拉到头的长表。
- ⚠️ `time_column` 会过**标识符校验**（`^[A-Za-z_][A-Za-z0-9_]*$`）——
  只读校验跑在替换**之前**，不校验的话注入内容会原样进到发出去的 SQL 里。
- ⚠️ **浏览 SQL 不要求 `$timefilter`** —— 那是**指标**的要求。浏览校验只看
  「只读 + 单语句」。
- `{start}` / `{end}` 的时间字面量同样按 `time_format` 生成（缺省 `iso_utc` + `UTC`）。

### 时序图：时间轴坐标由后端算

浏览页顶部有一张 **Grafana 风格的时序图**：x 轴是时间，y 轴是**值列**，
有分组列就每组一条线。

⚠️ **时间轴坐标（epoch 毫秒）由后端算，不在前端解析** ——

浏览响应的 `time_values` 用的是 `platform/sources/base.py:parse_time_column()`，
与**指标运行时同一份逻辑**（`iso_naive` 按源时区解释、`epoch_s`/`epoch_ms` 的单位、
`iso_utc` 的偏移处理都在这里）。

逻辑放两处必然漂移：浏览里画的图与真正跑出来的对不上，
而这正是浏览页存在的意义 —— 用户靠它确认「我以为的数据」就是「跑出来的数据」。

- ⚠️ 解析不出来的行给 `null`（断点）—— **绝不画到 1970 年**。
  那样看着像「数据都在 1970 年」，比空白更误导。
- `time_values` 为 `null`（整体）表示**没有时间列** → 不画图。
- ⚠️ 浏览里的时间解析是**宽松**的（坏值变断点），
  指标运行时是**严格**的（坏值直接让任务失败）——
  浏览是探索性的，一行坏时间不该让整个查询失败。

### 图上画的是「值列」，不是猜的

图的 y 轴取**角色指派**里的值列 —— 也就是用户在列头下拉里定的那一列。
没指派就不画图，并提示还差什么（而不是给一个空白框让人以为「这个源没数据」）。

⚠️ **时间列变了会自动重跑**（400ms 去抖）——
不重跑的话，用户换了时间列还得手动再点一次「执行」，
图停在旧的那一列，看着像「改了没反应」。

⚠️ y 轴**不从 0 起**（Grafana 的做法）—— 边界自己算：
向下取整、向上取整到 1 位有效数字的台阶。
不用 ECharts 的 `scale: true`（它只是「不强制含 0」，随后的 nice 取整仍会把 min 拉回 0），
也不用 `min: 'dataMin'`（那会把 `12.0746815396624` 这种原始值当刻度标签）。

### 错误码

| 情形 | 状态码 |
|---|---|
| 数据源不存在 | 404 |
| 本地校验失败（非 `SELECT`/`WITH` 开头、多语句、写关键字） | 400 |
| `$timefilter` 缺 `time_column` | 400 |
| `time_column` 不是合法标识符 | 400 |
| 数据源 `kind` 非法（库里被改坏） | 400 |
| 配置不一致（body 里的 `format` 与配置对不上） | 400 |
| **本地** SQL 写错（表不存在、语法错…） | 400 |
| 远端执行失败（远端 4xx/5xx、连不上） | 502 |
| 响应无法解析（非法 JSON/CSV、`rows_path` 不存在） | 502 |
| 请求超时 | 504 |

「远端 SQL 错」与「本地 SQL 非法」都会出现 —— 用**状态码**区分：远端挂了就 502，
用户写错就 400，界面直接显示，不用去猜。

⚠️ 「配置不一致」也是 400 —— 那是**用户配错了**，不是远端挂了；而远端返回的
解析失败（非法 CSV 之类）仍然是 502。两者都是 `ValueError`，靠专门的异常类型
（`ConfigError`）区分。

### 前端

数据源详情页挂「浏览数据」面板：SQL 编辑器 + 时间范围 + **时间格式** +
**源时区** + 结果表格。

⚠️ 时间格式与源时区**必须跟着请求一起发** —— 浏览与指标运行时用同一套
`$timefilter` 渲染（D11），浏览不声明的话，epoch / `iso_naive` 源的预览
≠ 跑出来的。

结果表格里每个列旁一个下拉（`时间列` / `值列` / `分组列`），点一下即填入对应字段，
再一键生成指标（`TIMESTAMP` 列自动推断 `time_format = iso_utc`；
`INTEGER` 列则要选 `epoch_s` / `epoch_ms` —— 按纳秒解释会静默落到 1970 年）。

## 假远端时序数据库

HTTP 透传需要**一个真的远端**才能演示与验证。项目自带一个：
照 **InfluxDB 3** 的 API 形状实现 `POST /api/v3/query_sql`，
后台线程持续造数。

```bash
make mock-tsdb              # 假远端 → http://127.0.0.1:8181/api/v3/query_sql
make mock-demo              # 平台侧建好 HTTP 数据源 + 指标 + 告警任务
make serve                  # 打开 http://127.0.0.1:8000/sources
```

或者一条命令全起（前端 + 后端 + 假远端）：

```bash
MOCK_TSDB=1 make dev
```

### 为什么照抄 InfluxDB 3

抄的是**接口形状**（端点路径、请求体 `{db, q, format}`、`format` 的取值），
不是它的查询引擎 —— 内部用 SQLite 存数据并执行 SQL。
照抄之后，**换 url + token 就能接真 InfluxDB 3**。

⚠️ 已知简化（**这是假远端的简化，不是平台的简化**）：

| 简化 | 说明 |
|---|---|
| 不实现鉴权 | `Authorization` 头**接受并忽略**。真库怎么鉴权是连接器 `config.headers` 的事，平台侧已经做完了 |
| JSON 不是两段式 | InfluxDB 3 的 `format=json` 返回 `results[].series[]`，平台的 `rows_path` 够不着。**接 InfluxDB 3 请用 `format=csv`**（也是官方推荐），假远端的 CSV 与真库一致 |
| `db` 不校验 | 只有一个库，字段存在即可（照抄的是「有这个参数」这个形状） |
| 不支持 `pretty` / `parquet` | 明确报 400，不静默降级。parquet 需要 pyarrow，本项目零新依赖 |

### 造出来的数据

表结构 `metrics(ts TEXT, series TEXT, value REAL)`，7 条序列，
刻意做成不同的形态，让平台的检测器有东西可测：

| 序列 | 形态 | 演示什么 |
|---|---|---|
| `web-traffic` | 日周期（每天一个波峰）+ 噪声 | 正常基线，不该报警 |
| `api-latency` | 平稳 + 抖动，偶尔**值为 NULL** | 噪声大但不异常；`missing_policy` 的用武之地 |
| `db-pool` | 日周期 + **尖峰**（每 30 点一次） | 该报尖峰型异常 |
| `cache-hit` | 日周期 + **漂移**（后段基线线性上移） | 该报漂移型异常 |
| `trend-load` | **线性趋势**（整条曲线都在涨） | 趋势不该被误报 —— IQR 这类只看分位数的检测器对它天然不敏感 |
| `step-cache` | **水平跳变**（每 3 小时切一次） | changepoint：该报的那一下要抓住，之后不反复报 |
| `job-runs` | **稀疏事件**（绝大多数点是 0，偶尔一个脉冲） | 统计型检测器的**盲区** —— 见下 |

⚠️ **断流**与**值缺失**是两件事，假远端两种都造：

- **断流**：那段时间**根本没有行** → 序列点数变少；
- **值缺失**：有行但值是 NULL → 平台的 `missing_policy` 真正生效的路径。

⚠️ 后三条是**形态演示**用的 —— 它们展示的是「不同检测器各有各的盲区」。

⚠️ **`job-runs` 上统计型检测器会「失明」**（实测）：

- 窗口里 75% 分位数仍是 0 → **IQR = 0** → 分数算不出来（除零）；
- 平台当前把算不出来的分数**按 0 处理**（不报）→ 界面显示「一切正常」；
- **Chronos 能报出来**（分数是 [0,1] 的相对越界程度，不依赖分位数尺度）。

⚠️ 所以这条曲线在默认的 `mock-tsdb-job`（用 Chronos）上会正常告警；
换成 `iqr` / `mad` 就一条都不报 —— 这不是数据的问题，是**检测器的盲区**。

⚠️ 「算不出来的分数按 0 处理」是个**已知的静默失效**（界面显示「一切正常」，
实际是「算不出来」）—— 记在 [ROADMAP.md](ROADMAP.md) 的待办里。

⚠️ **改了曲线定义就要重建库** —— db 里存的是按旧定义造的历史数据，
新增曲线在旧库里根本没有那段历史。库会记下序列定义的**指纹**，
对不上就**明确报错**（而不是静默跑出一堆错位的数据）：

```bash
rm -rf data/mock_tsdb/     # 删掉假远端的库
make mock-tsdb              # 重新起
```

### 几个关键约束

- **时间字面量统一 `+00:00`**（T 分隔 + 偏移）。SQLite 对 TEXT 列做**字典序**比较，
  格式不统一 → 边界行的比较结果会错（真 InfluxDB 3 用 timestamp 类型比较，没有这个问题）。
- **数据自己开 WAL**。平台以 `mode=ro` 打开它 —— WAL 让写者不阻塞读者，
  只读连接能读到已提交的最新数据。
- **时间锚点持久化**在库里。否则每次重启 index 0 都对应「现在」，
  同一个 index 有了不同时间戳，历史数据会重影。
- **`{sql}` 放 body 不放 url** —— body 里是原样替换，SQL 不会被百分号编码污染。
- **body 与 config 的 `format` 必须一致** —— 否则平台当场报 400。

### 数据不会无限增长

假远端只保留**最近 6 小时**的数据（滚动删除），并把数据放在**独立目录**
`data/mock_tsdb/` —— 不碰平台的 `data/platform/source.db`，
平台的保留策略（runs 表 / npz 目录 / feedback）也管不到它。

## 告警规则：缩放因子 × 等级

告警是异常检测的**后处理步骤**，不是独立引擎：没有事件生命周期、没有通知、没有抑制，
只有一层「检测输出 → 等级」的规则映射（实现见 `src/anomaly_lab/platform/alerts.py`）。

任务配一组规则，每行一条，**从上到下按严重程度排列**：

```
1, P2          # 倍数条件（主判定）：偏离基线 1 倍正常波动 → P2
3, P1          # 倍数条件：偏离基线 3 倍 → P1
>50, P0        # 绝对值条件（并行补充）：值 > 50 → P0
```

两类条件：

| 条件 | 写法 | 含义 |
|---|---|---|
| 倍数条件 | `3, P1` | 分数 ≥ 3 命中。**主判定** |
| 绝对值条件 | `>50, P0` | 实际值 > 50 命中。支持 `>` `>=` `<` `<=` |

- 「倍数」就是缩放因子（scaleFactor）：**倍数越大越保守**（告警越少、漏报越多），**倍数越小越灵敏**（告警越多、误报越多）。
  这与 CloudWatch 的 anomaly detection threshold 方向一致（`std_devs` 越大 → 带越宽 → 告警越少）。
- 命中多条规则时**取最高档**；倍数条件用「达到即命中」（`分数 >= 倍数`）。
- **列表顺序即档位顺序**（最后一行最严重）；等级名是自由字符串（`P2` / `P1` / `P0` 或自定义如 `注意`）。
- 绝对值条件**只抬不压**：它能把一个分数正常的点抬到高等级，但不会把分数判定出的高等级压低。
- 上下界带用**最低档的倍数条件**：带外即至少触发最低等级；更高等级用不同颜色标点。
- 留空规则则回落到默认两档（2.5 → P1，3.75 → P0）。
- **规则表可以只有绝对值条件**（2026-10-30 起不再报错）：没有倍数条件就没有「上下界宽度」，
  此时上下界带用**检测器自己的惯用阈值**（各检测器的 `default_threshold`），
  告警分级仍由规则表决定 —— 绝对值条件照常生效。
  这样 Chronos 的 `>=0.5, P1` 这种自然写法才能用（它的分数是 0~1，没有「倍数」可言）。

### 阈值可以改了

任务配置页与新建任务表单都是**档位并排的可编辑控件**（P1 一组、P0 一组），
不是纯文本框 —— 2.5 / 3.75 恰恰是最该被调的东西，
把它藏在一个要手写「2.5, P1」文本框里，等于把最常改的配置锁起来。

`PATCH /api/platform/jobs/{id}` 现在接受 `alert_rules`：

```json
{ "alert_rules": [ {"multiplier": 2.5, "level": "P1"},
                   {"multiplier": 3.75, "level": "P0"} ] }
```

⚠️ **规则表与阈值必须一致**，两边互为快捷视图：

| 改了谁 | 另一边怎么动 |
|---|---|
| 只改阈值 | 规则表**重算**成默认两档（`P1 × 阈值`、`P0 × 阈值×1.5`） |
| 改了规则表 | 阈值**同步**成规则表里的最低/最高档倍数 |
| 两者都改 | 规则表优先（用户更具体的选择） |
| 换了算法（跨量纲族） | 倍数**重算**成新算法的默认档；**绝对值条件保留** |

⚠️ 绝对值条件（`值 > 50 记 P0`）与量纲无关，换算法、改阈值都**不该**把它弄丢。

⚠️ 规则表的**倍数必须从小到大**且**不能重复** —— 顺序即档位顺序，
乱序会让「P0（最严重）比 P1 更容易触发」。前端会提示这种冲突。

⚠️ **换算法跨量纲族时阈值必须换**（分数的量纲变了），
但**同一次调用里显式给了规则表**就以规则表为准 —— 那是用户更具体的选择。

## 告警记录

`GET /api/platform/alerts` 跨任务汇总告警事件，前端在 `/alerts` 页面。

- **一条事件 = 一段连续告警点**：`severity > 0` 的连续点合并成一个区间，
  中间隔着正常点就断开。区间里的档位取**最高**的那一档（最严重的代表整段），
  另附区间内的峰值分数与点数。
- **以每个任务的最新一次运行为准** —— 平台任务是滚动窗口，同一段异常会被
  连续多次运行重复报出；扫全部历史 run 会让同一个异常出现很多遍。
  语义是「当前各任务处于什么告警状态」。
- 筛选参数：`job_id` / `level`（档位名）/ `series_id` / `since` / `until`
  （事件**开始时间**落在区间内）。
- 响应里的 `levels` / `series` / `jobs` 是下拉候选项，**从实际数据汇总**，不是硬编码。
  ⚠️ 候选值取自**未筛选**的集合 —— 否则选了 P1 之后下拉里就只剩 P1，
  筛选器把自己锁死了。
- **没被纳入统计的任务会出现在 `skipped` 里并说明原因**
  （还没跑过 / 运行失败 / 运行中 / 结果文件缺失），不会静默消失。

## 概览

`GET /api/platform/overview` 一次请求拿全整个平台的运行概况，前端在 `/` 页面。

- `counts`：数据源 / 指标 / 任务（含启用数）
- `runs`：累计运行、成功、失败、运行中
- `alerts`：总数、按档位、按任务、告警最多的序列、未纳入统计的任务数
- `feedback`：总数与按类型分布
- `jobs`：每个任务 + 它最近一次运行（序列数 / 告警数 / 耗时 / 错误）

> ⚠️ **不让前端自己去拼** —— 那样每个任务都要单独查 runs 与 feedback，
> 概览页（登录后第一屏）会发出 N+1 个请求。
> store 侧用 `run_stats` / `latest_runs` / `feedback_stats` 三个一次查询拿完。

> 事件里的 `level` 是**档位名**，来自任务的规则表 —— 可能是 P0/P1，
> 也可能是自定义的「注意」。`level_index` 才是严重度序（越大越严重）。

告警的**逐点明细**不在数据库里：它躺在每次运行的 npz 里（逐点 `severity` 数组）。
但**区间级明细在库里**（`alert_events` 表）——
runner 写库时就把连续告警点合并成区间存下来了，
查询期直接读，不再现场扫 npz。

⚠️ 保留策略 prune 掉运行目录时，`alert_events` 的行跟着外键级联删 ——
告警历史与运行历史同生共死。

## 基线与告警分级

平台只接受能给出上下界的算法：`iqr` / `mad` / `zscore` / `seasonal` / `stl_residual` /
`trend_residual_iqr` / `theil_sen`。

⚠️ `deseasonalized_iqr` 是 `trend_residual_iqr` 的**旧名** ——
那个名字说的是「去季节化」，做的却是「去**趋势**」。
旧名仍然可用（历史任务配置、评测产物里都是它），但下拉清单里只出现新名。

- **分数越大越异常**，语义与离线评测一致（`score_type` 见 [ALGORITHMS.md](ALGORITHMS.md)）。
- **基线**：该算法认为的「正常值」曲线（IQR 类是稳健中位数，Seasonal 是相位中位数，STL 是趋势+季节拟合）。
- **上下界**：基线 ± 最低档倍数 × 鲁棒尺度。
- **分级**：按上节的规则表判定；「从 10 突增到 50 算 P0 还是 P1」没有通用答案，所以由用户用倍数配等级。
- **周期自动估计**：`seasonal` 与 `stl_residual` 的周期按序列自动检测（FFT 找候选 + ACF 裁决，
  见 [ALGORITHMS.md](ALGORITHMS.md)），不再写死 24——5min 粒度下 24 点只有 2 小时，而日周期是 288 点。
  拿不准时**不猜**：周期不可信时 `seasonal` 退化成全局稳健统计，而不是用一个瞎猜的周期做相位分组
  （实测非周期类 F1 反而提升 0.03~0.07）。周期估计的坑见 [PITFALLS.md](PITFALLS.md)。

## 算法选择：默认自动推荐，也可指定

任务的「算法」可以填 `auto`（**默认**）或具体算法名。

`auto` 的做法是**按序列各自推断**（一条指标 group by 出多条序列时，可以各用各的算法）：

1. 用形态分类器判断该序列的形态（`stationary` / `periodic` / `trending` / `step` / `high_zero_ratio` / `sparse_event`）；
2. 形态 → 推荐检测器（见 `classification/recommend.py`），取第一个**平台支持**的候选；
3. 推断不出（点数少于 30、推荐的算法平台不支持）就**如实回退**并记录原因，不静默换掉。

结果落在 `index.json` 的每条序列上（`detector` / `metric_class` / `fallback`），预览页会显示
「自动 → 实际算法」与推断依据，**用户可以随时改成指定算法**。

> 这些检测器的分数量纲一致（都是「偏离基线多少个尺度单位」），所以同一套倍数规则可以跨检测器使用。
> 但**尺度本身的估计方式不同**（STL 残差的 MAD 通常远小于全局 MAD），同一份数据在不同算法下
> 分数量级可能差很多——下节对比表里的「惯用倍数」列就是解读这个差异的参照。

### 趋势型序列：必须先去趋势

⚠️ **趋势型序列直接跑 IQR 会大幅漏报** —— 这是**静默失效**：
界面显示「一切正常」，实际是「漏了 3/4 的异常」。

原因：IQR 用的是**全局**分位数。序列在涨时，整体分布被拉宽 →
四分位距变大 → 围栏跟着变宽 → 真正的突变点淹没在里面。

合成集 20 条 `trending` 序列（真异常 609 点）的实测：

| 算法 | 点级 F1 | 调整 F1 | 召回 | 精确率 |
|---|---:|---:|---:|---:|
| `iqr` | 0.317 | 0.435 | 20.2% | 95.0% |
| `mad` | 0.317 | 0.435 | 20.2% | 95.0% |
| `trend_residual_iqr` | 0.638 | 0.750 | 51.8% | 97.4% |
| **`theil_sen`** | **0.650** | 0.752 | **52.9%** | **98.3%** |

单条序列 `trending-2057-500` 的对比（检测记录页可直接查）：

| 算法 | Recall | F1 | Range-F1 |
|---|---:|---:|---:|
| `iqr` | 0.250 | 0.400 | 0.146 |
| `trend_residual_iqr` | 0.944 | 0.739 | 0.607 |
| `theil_sen` | **1.000** | **0.783** | **0.643** |

两个去趋势算法：

| | `trend_residual_iqr` | `theil_sen` |
|---|---|---|
| 趋势线 | 最小二乘（`polyfit`） | **Theil-Sen**（点对斜率的中位数） |
| 抗离群点 | 弱 —— 一次尖峰就能把趋势线拽歪 | **强** —— 少数点对影响不了中位数 |
| 残差尺度 | IQR | MAD（×1.4826，正态一致） |
| 默认阈值 | 2.5 | 3.5 |

⚠️ **Theil-Sen 的阈值是 3.5 不是 2.5** —— 这是**实测**出来的：
k=2.5 时精确率只有 73%（每 4 个报出有 1 个误报），
k=3.5 时精确率 98.3% 而召回只掉 2.6 个百分点，明显更划算。

⚠️ **估趋势用清洗值，打分用原始值** —— 估趋势时先 `winsorize`（离群点裁掉，
趋势线更稳），但**残差仍用原始值**：异常点必须留在残差里，
否则检测器就看不见它了。

`auto` 对趋势型序列会选 `theil_sen`（`classification/recommend.py` 的 `trending` 规则）。

### Chronos：预训练模型是例外，规则写法不一样

平台也支持 `chronos`（预训练时序模型），但它**不是**上面那类检测器，有三处不同：

| | 统计检测器 | Chronos |
|---|---|---|
| 分数量纲 | 偏离基线多少个尺度单位 | 按序列 min-max 归一化到 **[0,1]** 的相对越界程度（`score_type = prob`） |
| 基线与上下界带 | 有 | **没有** —— 预览图只有实际值与分数曲线 |
| 速度 | 约 0.06 毫秒/序列 | 约 **0.3 秒/序列**（chronos-2，CPU） |

因此：

- **告警规则要用绝对值条件写**：`>=0.5, P1` / `>=0.75, P0`。
  写倍数条件 `0.5, P1` 也对（分数 ≥ 0.5 即命中），但读起来容易误解。
  新建任务时选 Chronos 会自动预填这两档。
- **不会画基线带** —— 这不是 bug，是它没有基线。前端会显示「该算法未提供基线带」。
- **慢**：一条序列约 0.3 秒，一条指标 group by 出几十条序列时一次运行要几分钟。
  定时任务的执行间隔要留足（建议 ≥ 5 分钟），否则会一直追不上。

### ⚠️ 换算法时阈值会自动换

分数量纲不同，阈值**不能跨族沿用**：

| 族 | 分数是什么 | 阈值 |
|---|---|---|
| `scale`（统计型） | 偏离基线多少个尺度单位 | 2.5 / 3.5 这类倍数 |
| `prob`（Chronos） | 序列内 min-max 归一化的相对越界程度 | 0.5 / 0.75 |

把一个 `iqr` 任务改成 `chronos` 后如果还留着 `2.5×` 的阈值 ——
分数**永远到不了 2.5**，于是规则一条也不命中、告警永远是 0，
而界面显示「一切正常」。那是**假的**（静默失效，比报错还糟）。

所以平台在**跨族换算法**时会自动把阈值换成新算法的默认值（规则表跟着重算）：

- 统计型 → Chronos：阈值变成 `0.5 / 0.75`
- Chronos → 统计型：阈值变成 `2.5 / 3.75`

⚠️ 只有在**没有显式指定阈值**时才自动换 —— 用户手填的阈值是他自己的决定。
⚠️ 前端会提前提示「阈值会自动换成 X」，免得保存后阈值「莫名其妙变了」。

#### 同族换算法：分得清「继承的默认值」与「用户调过的值」

同族（都是 `scale`）换算法时**量纲没变**，阈值原则上可以沿用。
但同族不等于**同一个尺度** —— IQR 尺度、MAD 尺度、去趋势后的残差 MAD 是三把不同的尺，
所以每个算法的**惯用阈值本来就不一样**：

| 算法 | 惯用阈值 |
|---|---:|
| `iqr` | 2.5 |
| `mad` / `stl_residual` | 3.5 |
| `zscore` | 3.0 |
| `theil_sen` | 3.5（实测值） |

⚠️ 所以「同族沿用旧阈值」有个**盲点**：它分不清
「用户特意调过的阈值」与「从来没动过的默认值」。

后果很实在：用户从没调过阈值（用的是 iqr 的默认 2.5 / 3.75），
从 iqr 换到 `theil_sen` 后继续用 2.5 —— 精确率从 98% 掉到 73%，
而界面**一点提示都没有**。

现在的判据：

| 情况 | 阈值 |
|---|---|
| 跨族换算法 | **自动**换成新算法的惯用阈值 |
| 同族换算法，且两个阈值**都恰好是旧算法的默认值** | **自动**换成新算法的惯用阈值（那是继承来的，不是用户选的） |
| 同族换算法，且用户**动过**其中任何一个 | **保留**用户的值 |
| 显式指定了阈值 / 规则表 | 以用户给的为准 |

⚠️ 前端在算法下拉里**显示每个算法的惯用阈值**（「稳健趋势线 Theil-Sen（惯用 3.5）」），
用户换算法时就知道该把阈值调成多少。

**两个 Chronos 模型**（用 `ANOMALY_LAB_CHRONOS_MODEL` 切换）：

| 模型 | 权重 | 速度（合成集 6 条形态实测） | 平均 F1 |
|---|---:|---:|---:|
| `amazon/chronos-2`（**默认**） | 456 MB | 326 ms/序列 | 0.210 |
| `amazon/chronos-t5-tiny` | 44 MB | 4021 ms/序列 | 0.184 |

chronos-2 快 12 倍且 F1 略高（t5 是自回归逐 token 生成，chronos-2 是一次性预测），
代价是权重大 10 倍、首次下载要几分钟。

**可用性**：Chronos 需要 `chronos` 包 + **本地权重缓存**。本项目环境里
huggingface.co 不可达，所以运行期一律**离线加载**（`local_files_only=True`）——
不加这个参数时，首次加载会先退避重试 **~540 秒**才报错（实测 542 秒，
而真正装载只要 0.05 秒），而且每次重启服务都要重付这 9 分钟。

权重要先下载好：

```bash
# 国内网络走 hf-mirror 镜像
HF_ENDPOINT=https://hf-mirror.com .venv/bin/python scripts/download_chronos.py

# 换模型（默认 amazon/chronos-2）
ANOMALY_LAB_CHRONOS_MODEL=amazon/chronos-t5-tiny \
  HF_ENDPOINT=https://hf-mirror.com .venv/bin/python scripts/download_chronos.py
```

权重不在缓存里时，`/api/platform/catalog` 会把 chronos 标成 `available: false`
并给出原因，前端下拉里禁用它；建任务时也会直接 400 拒绝，不会等到定时任务
跑起来才看到一个失败的运行记录。

> `auto` **不会**选中 Chronos —— 形态推荐的候选里只有统计检测器，
> 预训练模型不会被自动带进定时任务。

> **Chronos-2 需要单独的加载路径**：`Chronos2Pipeline.from_pretrained` 第一件事是查
> 「是不是 LoRA 适配器」，那个调用既不接受 `local_files_only` 也不看 `HF_HUB_OFFLINE`
> （后者在 transformers import 时就被求值缓存了），网络不通时会重试 5 次、每次超时。
> 所以代码里绕开了它，直接用 `AutoConfig` + `Chronos2Model` 加载。

### 自动推荐在公开真实数据上的实测表现

```bash
make validate-auto      # 首次会自动下载 NAB 到 data/cache/nab/
```

用 NAB（Numenta Anomaly Benchmark，52 条真实序列 + 点级异常标签）实测：

| 算法 | 点级 F1 | 窗口级 F1 |
|---|---:|---:|
| `zscore` | 0.106 | 0.116 |
| `trend_residual_iqr`（旧名 `deseasonalized_iqr`） | 0.067 | 0.068 |
| `iqr` | 0.059 | 0.060 |
| `mad` | 0.054 | 0.055 |
| `seasonal` | 0.023 | 0.031 |
| `stl_residual` | 0.007 | 0.007 |

`auto` 的表现：平均 F1 0.057 / 平均排名 3.02 / 夺冠率 13.5% / 回退率 0%。

**结论要诚实说：auto 在这批真实数据上并没有跑赢「固定用 zscore」（-0.049），
只是与「固定用 iqr」基本持平（-0.002）。** 它现在的价值是「给个像样的起点 +
让人知道该去比哪几个算法」，而不是「比人挑得准」。

两个发现：

1. **回退率曾高达 69%**——36/52 条真实序列被判为 `step`，而 `step` 的首选算法
   `changepoint` 给不出上下界（平台不支持），于是全部回退到 `iqr`。
   修复方式是给推荐列表补上同类次选（`step` → `trend_residual_iqr`、
   `sparse_event` → `iqr`），回退率降到 0，auto 平均 F1 +36%。
2. **NAB 的标注特性与形态自适应算法的目标并不匹配**：NAB 的异常是极稀疏的点级标注
   （有的序列 4032 个点只标了 1 个异常），此时最不形态自适应、最敏感的 `zscore`
   反而在所有形态下都最好。所以这批数据能验证**工程问题**（回退率），
   但**不足以给 auto 的算法价值下定论**。

   佐证：NAB 标的是**语义异常**而非统计极值——`art_daily_flatmiddle` 被标为异常的点
   值是 40.0，而该序列的最大值是 87.96。形态自适应算法（seasonal / stl_residual）
   擅长的是「偏离统计基准」，对「中间变平了」这类语义异常反而不敏感。
   真实生产里的告警更接近后者——这也是为什么**反馈闭环**比自动选算法更关键。

> 诚实性声明：第 1 点的修复是在看过 NAB 结果之后做的，因此这一轮评估
> **不再是完全独立的泛化验证**。要重新评估应换一个未参与调参的公开集。
> 项目自身的原则「公开集只用于泛化验证，不用于调参」在这里被破坏了，
> 因此 NAB 已被「用掉」，后续评估应换数据集。

## 多算法对比：选算法时看对照

预览区勾选「多算法对比」，同一条序列会用多个算法**各跑一遍**，返回各自的基线、上下界与告警点。

- **同一套倍数规则**：所有算法用任务当前的规则表判定，所以告警数可以直接横向比较
  （「同样的敏感度下谁更吵」）。
- **默认对照组**：任务配置的算法 + auto 推荐的候选组（如 `seasonal` / `stl_residual` / `iqr`），
  默认**全部并列展示**——形态模糊时不必盲选，直接比。
- **同时给出 auto 的推断**：形态、置信度、选中的算法、是否回退、推荐理由。
- **一键选定**：每行有「设为任务算法」按钮，把任务固定成你选定的算法
  （`PATCH /api/platform/jobs/{id}` 传 `detector`）。
- 只是探索功能：不产生告警、不落盘。

实测同一条周期型序列（500 点，倍数 1.0）：

| 算法 | 告警数 | 最高档 | 最高分 | 惯用倍数 |
|---|---|---|---|---|
| `iqr` | 6 | 0 | 3.75 | 2.5 |
| `seasonal`（auto 选中） | 25 | 8 | 13.27 | 2.5 |
| `stl_residual` | 82 | 36 | 37.04 | 3.5 |

这张表就是「为什么周期型要用 seasonal」的答案：全局 IQR 把季节性当异常（**漏**），
而 STL 残差在同一份数据上最吵（**过**）。auto 选中的 `seasonal` 落在中间。

## 反馈与调参：评估 → 检测 → 优化的闭环

真实数据没有异常真值，所以评估靠**人工反馈**。这里完全对齐 AWS 的做法：

| | AWS | 本平台 |
|---|---|---|
| 反馈粒度 | 时间范围（Start/End time） | 时间范围（`start_ts` / `end_ts`） |
| 反馈类型 | Correct / False alarm / Missed / Other | `correct` / `false_alarm` / `missed` / `other` |
| 闭环动作 | 自动调 band 宽度与学习率 | 在候选倍数上比较 precision/recall，给出建议倍数 |

评估逻辑（`platform/feedback.py`）：

- `missed` 区间是**正例**（该报没报），`false_alarm` 区间是**负例**（不该报却报了）；
- 候选 = **算法 × 倍数**的组合：对每个候选算法重跑一次检测拿到分数，再对每档倍数算表现；
- 目标函数自适应：有正反例时最大化 **F1**；只有漏报时最大化 **召回**；只有误报时**最小化误报点数**；
- **同等效果下取最小干预**：能消掉误报的最小倍数就够，不一路推到极端（AWS 也是渐进调整）；
  同等效果时**优先不改算法**（调阈值比换算法便宜）；
- 没有可用反馈时**不给建议**，绝不猜；反馈少于 3 条会提示样本偏少。

所以建议有两类：

| 情形 | 建议 |
|---|---|
| 误报来自**阈值太松** | 「把最低档倍数从 1 调到 2（更保守）」 |
| 误报来自**算法不合适**（阈值怎么调都消不掉） | 「建议把任务固定为 `iqr`（而不是 `seasonal`）」 |

`auto` 模式下，系统把 auto 本身也当作一个候选参与比较——它是「每条序列各挑一个算法」的
**混合表现**，不是单个算法。所以建议里不会出现生硬的「从 auto 换成 X」，
而是「自动选择在这段区间上不合适，建议固定为 X」。

指标口径上刻意保守：缺正例就没有 `recall`、缺负例就没有 `precision`，如实留空而不是拿 1.0 冒充完美。

应用建议（`POST /api/platform/jobs/{id}/apply-suggestion`）会**按比例整体缩放**规则表里的倍数条件，
保持各档之间的相对关系不变（最低档 1→2 时，最高档 3→6），并可同时固定算法。

## 删除

```
DELETE /api/platform/jobs/{job_id}
DELETE /api/platform/metrics/{metric_id}
DELETE /api/platform/sources/{source_id}
```

- **级联删除**：删数据源会连带删掉它下面的指标、任务、运行记录与人工反馈。
  数据库层靠 `ON DELETE CASCADE` + `PRAGMA foreign_keys=ON`（schema 里早就写好了）。
- **run 目录文件会一并清理** —— 数据库外键管不到文件系统，
  不清的话 `cache/platform/runs/{run_id}/` 会变成孤儿垃圾。
- **运行中的任务删不掉**：返回 409「任务正在运行中，请等本次运行结束后再删除」。
- 响应体 `{"deleted": {"jobs": 1, "metrics": 2, "runs": 5, "feedback": 3}}`
  给出连带删除的统计。
- 前端在三个列表页提供入口，确认弹窗会写明**连带删除的数量**
  （影响范围从 `catalog` 自己算，不另开端点）。

## 检测记录：筛选与分页

`/detections` 是回测侧的**检测记录页**：左栏是记录索引，右栏是选中那条的检测详情图。

### 一条记录是「序列 × 算法」

同一条序列在不同检测算法下是**两条不同的记录**。所以：

- 列表项显示「序列名 + 算法标签」，只显示序列名分不清；
- 高亮按 **(序列, 算法)** 匹配 —— 只按序列比会把同序列的所有算法一起点亮；
- URL 同时带 `series_id` 与 `detector`：`/detections?series_id=...&detector=mad`，
  评估报告页的链接也照此生成。

### 筛选与分页

筛选栏五个维度（时间范围 / 检测算法 / 形态 / 来源）与**评估报告页共用同一个组件**
（`features/evaluation/FilterBar.tsx`）—— 同一份数据、同一套筛选逻辑，
分两处维护必然漂移。筛选逻辑是 `filterRows` / `distinctValues`，在前端执行
（`/api/summary` 已经把全部记录返回了）。

左栏每页 20 条，分页器在**滚动区之外** —— 侧栏是 `overflow: auto` 的，
分页器放进去就得滚到底才看得见，那等于没有分页。

- 深链接指向后面页的记录时，页码会自动拨到它所在的那页并高亮；
- 选中项被当前筛选排除时，详情头会说明「这条记录不在当前筛选结果里」。

### `/api/badcases?series_id=<id>&detector=<name>`

`detector` 是**可选**参数（默认 `iqr`，老调用方行为不变）。

⚠️ 它会拼进文件路径（`cache/detections/<detector>/<id>.npz`），
所以**必须校验**算法名 —— 非法名返回 400，不是 404 也不是 500。
合法的算法名里没有点也没有斜杠，而 `stl_residual` / `trend_residual_iqr` 这类都合法。

## 数据保留与清理

平台的任务每 5 分钟就产生一次运行记录（DB 一行 + 一个 npz 目录）。
不清理的话一年就是 21 万行、几个 GB —— 所以**超期的数据会自动清掉**。

### 保留期：只有一个维度 —— 时间

| 参数 | 环境变量 | 默认 |
|---|---|---|
| 保留多少天 | `ANOMALY_LAB_RETENTION_DAYS` | 180（6 个月） |

```
保留 = 该任务的运行中，`started_at` 还在最近 N 天内的
```

配 180 天就是留 180 天 —— **可预测**，跟 Prometheus / Grafana Cloud 的心智模型一致。

⚠️ **只有这一个维度**。曾经还配过「每任务最多留 N 次」，两个条件取交集，
结果是要解释「∩」、要测两套边界，收益却只是给高频任务兜底。
兜底该由**磁盘上限**做（见下），不该塞进策略里。

⚠️ 保留策略是**部署参数**，不是业务配置 —— 所以放环境变量而不是数据库。

### 磁盘上限（兜底，不是策略）

单任务的结果目录超过 **4 GB** 时，会额外删掉最老的运行。

- ⚠️ **保留期永远优先** —— 只有它兜不住时才生效。
  任务频率极高时（每 10 秒一次），「保留 180 天」要 27 GB，
  那时候宁可少留，也不能让平台因为磁盘写满而崩掉。
- 触发了会在清理结果里**说出来**（`disk_capped_jobs`），不藏着。

### 清什么

| 清 | 不清 |
|---|---|
| `runs` 表里超期的行 | **人工反馈**（`feedback` 表）—— 人工数据，删它等于丢弃用户的劳动成果 |
| `data/cache/platform/runs/<run_id>/` 目录 | **标注**（`data/annotations/`）—— 回测侧的人工标注 |
| **孤儿目录**（DB 里没有对应记录、目录还在） | **假远端的数据**（`data/mock_tsdb/`）—— 它自己滚动保留最近 6 小时，不归平台管 |
| | **回测侧的检测结果**（`data/cache/detections/`）—— `make detect` 的一次性产物 |

反馈的 `run_id` 会被置为 `NULL`（引用断开了，反馈本身留着）。
⚠️ 表里没有外键约束，所以这一步是**手动 UPDATE**，不是 `ON DELETE SET NULL`。

### 三条不能破的约束

1. **最新一次运行永远保留** —— 告警记录只读每个任务的最新 run
   （`collect_alert_events` → `latest_runs()`）。删了它整个告警页就空了：
   那不是「清理旧数据」，是**功能坏了**。
   ⚠️ 这在「任务停了半年、你打开平台看告警」时是刚需：
   那个任务不会再产生新运行，清理每轮都会把最后一条删掉，告警记录就**永久**空了。
2. **正在执行的运行不删** —— runner 还在往它的目录里写 npz，
   删了目录那次运行就会失败。**清理由别人触发、却把别人的运行搞坏** —— 不能接受。
3. **先删文件、再删数据库行** —— 两个方向都有自愈路径，
   但磁盘占用的释放才是本功能的主要目标。

### 触发方式

- **自动**：调度器每次 tick 后检查，**每小时最多清一次**
  （tick 默认 2 秒一次，每次都全表扫描太浪费）。清理失败只记日志 ——
  清理失败不该把调度线程带走。
- **手动**：`make prune` 或 `anomaly_lab.cli prune --dry-run`（先看会删什么）。
- **接口**：`POST /api/platform/prune`。

### 看得见

- `GET /api/platform/storage` —— 当前占用、保留策略、上次清理时间
- 概览页的「数据保留」卡片 —— 占用、策略、上次清理，外加「立即清理」按钮

⚠️ 概览页的「累计运行」因此改成了「**保留期运行**」——
清理后这个数字不再是无界的累计值，叫「累计」就是撒谎。

## 调度语义

- 内置调度器随 `serve` 启动（`--no-scheduler` 可关闭），单线程串行执行任务。
- 每个任务有 `next_run_at`；到点执行后推进到 `now + interval`，失败也推进（失败详情在 `runs` 表，不会重试风暴）。
- 进程重启时把「错过」的窗口收敛到现在，**只补跑一次**，避免停机越久补得越多。
- 停用任务（`enabled=0`）不会进入到期队列。

## 已知限制（第一版有意不做）

- 支持 SQLite 文件与 HTTP SQL 网关两种数据源；`kind` 已收敛为枚举（`sqlite` / `http`）。
  专有查询语言（InfluxDB 2.x 的 InfluxQL、Prometheus 的 PromQL）**仍待做** ——
  SQL 与 PromQL 不是同一种语言，无法自动翻译，得做成专用连接器。
- HTTP 源的 SQL **原样发到远端执行**，平台的只读校验只是第二道防线（关键字黑名单可绕过）；
  真正的安全边界是**远端账号的权限**，必须用只读凭据。
- 数据浏览器的结果**不落库**、不建指标，只是预览。
- 预处理（清洗/聚合）与取数在同一进程内完成，接口边界保留，但**没有**独立 worker 进程做内存隔离。
- 没有认证、多租户与权限；这是本地学习项目，不是可对外的服务。
- 多 worker 部署会各自跑一份调度器（当前按单进程使用设计）。
- 不做未来多步预测，上下界是「基线 ± 阈值 × 尺度」，不是统计意义上的预测区间。
- 形态分类仍是**单一归类**：形态模糊的指标（0~10 平稳波动但有周期）会被强行归到一类。
  目前的缓解手段是 `auto` 会记录推断依据与置信度、用户可覆盖；真正的解法是并列多个候选让用户选。
- 反馈是**区间级**的：一段区间里若既有真异常又有正常点，只能二选一标注，粒度损失换来了可用性。
- 反馈评估用的是**这次 run 的分数**，不重跑检测（便宜但意味着建议基于当时的判定结果）。
