# 平台垂直切片

把「数据源 → 指标 → 检测任务 → 定时执行 → 基线预览」串成一条可运行的链路，对应 [my-thought.md](my-thought.md) 里第一阶段的设想。

## 快速体验

```bash
make platform-demo          # 生成 demo 源库 + 指标 + 任务（写入 data/）
make serve                  # http://127.0.0.1:8000/platform
```

或者纯脚本冒烟（不启 Web）：

```bash
make platform-smoke         # 跑一次任务并断言：2 条序列、有告警
```

## 三层配置模型

| 概念 | 存哪 | 关键字段 |
|---|---|---|
| 数据源 Source | `data/platform.db` 的 `sources` | 名称、类型（当前只有 `sqlite`）、路径（相对数据根目录或绝对路径） |
| 指标 Metric | `metrics` | 数据源、SQL、时间列、值列、分组列、时间格式、源时区、缺失值策略、采样频率 |
| 检测任务 Job | `jobs` | 指标、算法（可填 `auto`）、告警规则表、窗口点数、执行间隔、启用状态 |

运行记录在 `runs`，人工反馈在 `feedback`，详细数组在 `data/cache/platform/runs/<run_id>/`（`index.json` + 每条序列一个 npz）。

## 时间语义：不猜，必须声明

时间列的存储形式与时区是**数据源的属性**，平台不做猜测（对应 CloudWatch 的 `MetricTimezone`）：

| `time_format` | 含义 | 例子 |
|---|---|---|
| `iso_utc` | ISO8601，自带时区或本身就是 UTC | `2026-01-01T12:00:00+08:00`、`2026-01-01T12:00:00Z` |
| `iso_naive` | 无时区墙钟时间，按 `source_timezone` 解释 | `2026-01-01 20:00:00` + `source_timezone=Asia/Shanghai` |
| `epoch_s` / `epoch_ms` | Unix 时间戳 | `1767268800` |

比较用 SQLite 内置的 `julianday()` 归一化，避开 ISO 字符串字典序比较的坑；`iso_naive` 会把查询边界换算成源时区的墙钟再比。

**声明错了的后果**：取不到数据 → 该序列标记为「数据不足」，而不是悄悄取错区间。

## 缺失值：自动兜底 + 可覆盖 + 绝不静默

| `missing_policy` | 行为 |
|---|---|
| `drop`（默认） | 丢弃缺失点，并记录丢弃了多少个 |
| `interpolate` | 按时间线性插值（适合采集抖动造成的空洞） |
| `error` | 严格模式：有缺失就判任务失败 |

**关键**：不管哪种策略，有效点少于 10 个的序列会被标记为 **数据不足（`insufficient_data`）**——既不算异常，也**绝不显示成「一切正常」**。这一条是硬约束：检测没跑起来不能长得像没异常。

## `$timefilter` 与 group by

指标 SQL 里必须**恰好有一个** `$timefilter`，执行时会被替换成时间条件：

```sql
SELECT ts, host, value FROM metrics WHERE $timefilter ORDER BY ts
```

执行时等价于（列名来自配置，已做标识符校验）：

```sql
SELECT * FROM (SELECT ts, host, value FROM metrics
               WHERE "ts" >= ? AND "ts" < ? ORDER BY ts) LIMIT 100001
```

- 时间范围用参数绑定，不做字符串拼接。
- 只允许 `SELECT` / `WITH` 开头的单条语句；含写操作关键字直接拒绝，连接以 `mode=ro` 打开。
- `group_column` 非空时，**在加载层就拆成独立序列**：序列 ID 为 `{指标名}:{分组值}`，检测器永远只面对一条序列。
- 单次查询上限 10 万行，超出要求缩小窗口或加聚合。

时间范围用参数绑定，时间列用 `julianday()` 比较（见上节）。

## 告警规则：缩放因子 × 等级

告警是异常检测的**后处理步骤**，不是独立引擎：没有事件生命周期、没有通知、没有抑制，
只有一层「检测输出 → 等级」的规则映射（实现见 `src/anomaly_lab/platform/alerts.py`）。

任务配一组规则，每行一条，**从上到下按严重程度排列**：

```
1, P2          # 倍数条件（主判定）：偏离基线 1 倍正常波动 → P2
3, P1          # 倍数条件：偏离基线 3 倍 → P1
>50, P0        # 绝对值条件（并行补充）：值 > 50 → P0
```

两类条件：

| 条件 | 写法 | 含义 |
|---|---|---|
| 倍数条件 | `3, P1` | 分数 ≥ 3 命中。**主判定** |
| 绝对值条件 | `>50, P0` | 实际值 > 50 命中。支持 `>` `>=` `<` `<=` |

- 「倍数」就是缩放因子（scaleFactor）：**倍数越大越保守**（告警越少、漏报越多），**倍数越小越灵敏**（告警越多、误报越多）。
  这与 CloudWatch 的 anomaly detection threshold 方向一致（`std_devs` 越大 → 带越宽 → 告警越少）。
- 命中多条规则时**取最高档**；倍数条件用「达到即命中」（`分数 >= 倍数`）。
- **列表顺序即档位顺序**（最后一行最严重）；等级名是自由字符串（`P2` / `P1` / `P0` 或自定义如 `注意`）。
- 绝对值条件**只抬不压**：它能把一个分数正常的点抬到高等级，但不会把分数判定出的高等级压低。
- 上下界带用**最低档的倍数条件**：带外即至少触发最低等级；更高等级用不同颜色标点。
- 至少要有一条倍数条件（否则定不出上下界宽度，配置期就报错）；留空规则则回落到默认两档（2.5 → P1，3.75 → P0）。

## 基线与告警分级

平台只接受能给出上下界的算法：`iqr` / `mad` / `zscore` / `seasonal` / `stl_residual` / `deseasonalized_iqr`。

- **分数越大越异常**，语义与离线评测一致（`score_type` 见 [ALGORITHMS.md](ALGORITHMS.md)）。
- **基线**：该算法认为的「正常值」曲线（IQR 类是稳健中位数，Seasonal 是相位中位数，STL 是趋势+季节拟合）。
- **上下界**：基线 ± 最低档倍数 × 鲁棒尺度。
- **分级**：按上节的规则表判定；「从 10 突增到 50 算 P0 还是 P1」没有通用答案，所以由用户用倍数配等级。

## 算法选择：默认自动推荐，也可指定

任务的「算法」可以填 `auto`（**默认**）或具体算法名。

`auto` 的做法是**按序列各自推断**（一条指标 group by 出多条序列时，可以各用各的算法）：

1. 用形态分类器判断该序列的形态（`stationary` / `periodic` / `trending` / `step` / `high_zero_ratio` / `sparse_event`）；
2. 形态 → 推荐检测器（见 `classification/recommend.py`），取第一个**平台支持**的候选；
3. 推断不出（点数少于 30、推荐的算法平台不支持）就**如实回退**并记录原因，不静默换掉。

结果落在 `index.json` 的每条序列上（`detector` / `metric_class` / `fallback`），预览页会显示
「自动 → 实际算法」与推断依据，**用户可以随时改成指定算法**。

> 这些检测器的分数量纲一致（都是「偏离基线多少个尺度单位」），所以同一套倍数规则可以跨检测器使用。
> 但**尺度本身的估计方式不同**（STL 残差的 MAD 通常远小于全局 MAD），同一份数据在不同算法下
> 分数量级可能差很多——下节对比表里的「惯用倍数」列就是解读这个差异的参照。

## 多算法对比：选算法时看对照

预览区勾选「多算法对比」，同一条序列会用多个算法**各跑一遍**，返回各自的基线、上下界与告警点。

- **同一套倍数规则**：所有算法用任务当前的规则表判定，所以告警数可以直接横向比较
  （「同样的敏感度下谁更吵」）。
- **默认对照组**：任务配置的算法 + auto 推荐的候选组（如 `seasonal` / `stl_residual` / `iqr`）。
- **同时给出 auto 的推断**：形态、置信度、选中的算法、是否回退、推荐理由。
- 只是探索功能：不产生告警、不落盘。

实测同一条周期型序列（500 点，倍数 1.0）：

| 算法 | 告警数 | 最高档 | 最高分 | 惯用倍数 |
|---|---|---|---|---|
| `iqr` | 6 | 0 | 3.75 | 2.5 |
| `seasonal`（auto 选中） | 25 | 8 | 13.27 | 2.5 |
| `stl_residual` | 82 | 36 | 37.04 | 3.5 |

这张表就是「为什么周期型要用 seasonal」的答案：全局 IQR 把季节性当异常（**漏**），
而 STL 残差在同一份数据上最吵（**过**）。auto 选中的 `seasonal` 落在中间。

## 反馈与调参：评估 → 检测 → 优化的闭环

真实数据没有异常真值，所以评估靠**人工反馈**。这里完全对齐 AWS 的做法：

| | AWS | 本平台 |
|---|---|---|
| 反馈粒度 | 时间范围（Start/End time） | 时间范围（`start_ts` / `end_ts`） |
| 反馈类型 | Correct / False alarm / Missed / Other | `correct` / `false_alarm` / `missed` / `other` |
| 闭环动作 | 自动调 band 宽度与学习率 | 在候选倍数上比较 precision/recall，给出建议倍数 |

评估逻辑（`platform/feedback.py`）：

- `missed` 区间是**正例**（该报没报），`false_alarm` 区间是**负例**（不该报却报了）；
- 候选倍数 = 绝对网格 ∪ 围绕当前倍数的相对网格，对每个候选重算告警判定，算出 TP/FP/FN/TN；
- 目标函数自适应：有正反例时最大化 **F1**；只有漏报时最大化 **召回**；只有误报时**最小化误报点数**；
- **同等效果下取最小干预**：能消掉误报的最小倍数就够，不一路推到极端（AWS 也是渐进调整）；
- 没有可用反馈时**不给建议**，绝不猜；反馈少于 3 条会提示样本偏少。

指标口径上刻意保守：缺正例就没有 `recall`、缺负例就没有 `precision`，如实留空而不是拿 1.0 冒充完美。

应用建议（`POST /api/platform/jobs/{id}/apply-multiplier`）会**按比例整体缩放**规则表里的倍数条件，
保持各档之间的相对关系不变（最低档 1→2 时，最高档 3→6）。

## 调度语义

- 内置调度器随 `serve` 启动（`--no-scheduler` 可关闭），单线程串行执行任务。
- 每个任务有 `next_run_at`；到点执行后推进到 `now + interval`，失败也推进（失败详情在 `runs` 表，不会重试风暴）。
- 进程重启时把「错过」的窗口收敛到现在，**只补跑一次**，避免停机越久补得越多。
- 停用任务（`enabled=0`）不会进入到期队列。

## 已知限制（第一版有意不做）

- 只支持 SQLite 一种数据源；`kind` 字段与 `Source` 模型已为后续插件（InfluxDB / Prometheus）预留。
- 预处理（清洗/聚合）与取数在同一进程内完成，接口边界保留，但**没有**独立 worker 进程做内存隔离。
- 没有认证、多租户与权限；这是本地学习项目，不是可对外的服务。
- 多 worker 部署会各自跑一份调度器（当前按单进程使用设计）。
- 不做未来多步预测，上下界是「基线 ± 阈值 × 尺度」，不是统计意义上的预测区间。
- 形态分类仍是**单一归类**：形态模糊的指标（0~10 平稳波动但有周期）会被强行归到一类。
  目前的缓解手段是 `auto` 会记录推断依据与置信度、用户可覆盖；真正的解法是并列多个候选让用户选。
- 反馈是**区间级**的：一段区间里若既有真异常又有正常点，只能二选一标注，粒度损失换来了可用性。
- 反馈评估用的是**这次 run 的分数**，不重跑检测（便宜但意味着建议基于当时的判定结果）。
