## 实现期设计校准（Chunk 1）

- **分类规则顺序修正**：计划中 `zero_ratio >= 0.6 -> high_zero_ratio` 会先吞掉稀疏事件（其零值占比约 99%）。实现改为先按“非零连续段数”判 `sparse_event`，再判 `high_zero_ratio`。
- **`changepoint_score` 改为大窗口中位数差**：原“全局两段均值差”对 drift / flatline 等短异常段过于敏感；改用变点两侧 20% 窗口的中位数差 / 全局 MAD，阶梯与趋势/短异常段可稳定区分。
- **`trend_strength` 改为 |Spearman ρ|**：OLS 斜率显著性会被异常段抬高残差方差，导致趋势型与阶梯型混淆。
- **周期检测收紧**：周期候选需满足 `n // p >= 3`；ACF 峰前需有明显低谷，且在 2 倍周期处仍保留相关性（排除单调衰减造成的伪峰）。
- **UCR 在线下载**：单序列 URL 仍未校准；在线路径需通过 `ANOMALY_LAB_UCR_SERIES_URL`（含 `{name}`）显式提供模板，否则只读缓存。

## 平台垂直切片（2026-10-29，第一版）

- **范围**：SQLite 单源 + SQL 指标（`$timefilter`）+ group by 拆序列 + 双向基线/上下界 + P1/P0 用户配置分级 + 内置定时调度 + 前端预览。详见 [PLATFORM.md](PLATFORM.md)。
- **调度语义**：重启后错过的窗口只补跑一次；失败也推进 `next_run_at`，避免重试风暴。
- **正确性修复（自查后）**：缺失值不再静默失效（引入 `missing_policy` 与「数据不足」状态）；时间语义改为显式声明 `time_format` + `source_timezone`（对应 CloudWatch 的 `MetricTimezone`），比较统一走 `julianday()`；SQLite 打开 WAL；preview 校验 run 归属；手动运行与调度并发时复用同一次 run；配置期校验频率；运行失败原因透传到 API。
- **告警规则表**：任务改为配置「倍数（缩放因子）→ 等级」规则列表（如 `1×→P2`、`3×→P1`），判定以异常分数为准、取命中的最高档；上下界带用最低档倍数；判定语义统一为「达到即命中」。告警定位为**检测的后处理步骤**（无事件生命周期、无通知、无抑制）。
- **绝对值条件并行**：规则表可混写绝对值条件（如 `>50, P1`），与倍数条件并行生效且**只抬不压**。2026-10-30 起不再强制「至少一条倍数条件」—— 没有倍数条件时上下界带用检测器的惯用阈值（`default_threshold`），分级仍由规则表决定。
- **自动推荐算法**：任务算法可填 `auto`（默认），运行时按序列各自做形态分类 → 推荐检测器；推荐不可用时如实回退并记录原因。分类结果已接入平台任务（不再是只有离线可用）。
- **自动推荐的实测（公开真实数据）**：NAB 52 条真实序列上，auto 平均 F1 0.057、平均排名 3.02、夺冠率 13.5%，**未跑赢固定用 zscore（-0.049）**，与固定用 iqr 基本持平（-0.002）。
- **顺带修的真实缺陷**：实测暴露出 **36/52 条真实序列被判为 `step`，而 step 首选算法 `changepoint` 平台不支持 → 回退率 69%**。修复：推荐列表补同类次选（step → deseasonalized_iqr、sparse_event → iqr），回退率 → 0，auto 平均 F1 +36%。
- **反馈闭环**：按 AWS 的做法实现时间范围级人工反馈（correct / false_alarm / missed / other），在候选倍数上比较 precision / recall，给出新的告警倍数建议并支持一键应用。评估口径保守：缺正例无 recall、缺负例无 precision，如实留空。
- **反馈驱动的算法调节**：建议范围从「倍数」扩到「**算法 × 倍数**」——评估时对每个候选算法重跑检测再比较，误报来自算法不合适时建议换算法（阈值怎么调都消不掉才会换）。原则是**最小干预**：调阈值能解决就不动算法；同等效果优先保持当前设置。`auto` 作为「逐序列各选一个」的混合表现也参与比较。
- **周期估计重做（FFT 找候选 + ACF 裁决）**：旧实现只用 ACF 且 lag 上限写死 200——5min 粒度的日周期（288 点）、周周期（2016 点）根本看不到，且 ACF 峰有 ±1 误差会让相位分组整体错位。新实现：FFT 列出全部局部峰交给 ACF 逐个裁决（避开谐波歧义——argmax 会选到 5 倍频）、谐波重复性作硬门槛（判结构不判幅度，对离群点鲁棒）、相位解释力作最终门槛、候选范围按**时间**表达（同一「一天」在 5min/15min/1h 粒度下都能认出）。实测：合成集 periodic 类周期精确命中 **20/20**、非周期误判 **0/100**（旧实现 15/20 精确、误判 1/100）。
- **周期性突刺的处理原则已确立**：每天固定时刻的规律突增属业务常态（相位统计会吸收它），而孤立突增才异常。配套的硬约定是「**清洗只用于估计，不用于打分**」——把异常点从打分输入里洗掉就是漏报。详见 [PITFALLS.md](PITFALLS.md)。
- **周期不可信时不猜**：Seasonal 在无可信周期时退化成全局稳健统计，而不是用一个瞎猜的周期做相位分组（实测非周期类 F1 从 0.305/0.216 提升到 0.347/0.284）。
- **⚠️ 但在 NAB 真实数据上各检测器 F1 没有变化**（seasonal 仍 0.023）——因为 NAB 的异常标注是稀疏的**语义异常**（标的是「中间变平了」而非统计极值），形态自适应算法在上面本来就吃亏，周期准不准都救不了。这再次说明 NAB 不适合评估形态自适应能力。
- **多算法对比**：预览区可同条序列并排多个算法（同一套倍数规则），同时给出 auto 的形态推断、置信度与推荐候选；每行可「一键设为任务算法」。选算法时不必盲选。
- **形态分类的并列候选已落地**：auto 的候选组默认全部并列展示，模糊指标由用户自己比着定，而不是被单一归类绑死。
- **AWS 对标结论**：CloudWatch 的告警反馈也是时间范围级（Correct / False alarm / Missed），系统自动调 band 宽度与学习率；Lookout for Metrics 用「用户对异常的相关性反馈」持续提升准确率；Lookout for Equipment 依赖领域标签（故障时间段）当真值。三者都印证：**真实数据没有现成真值，反馈闭环是唯一出路**。
- **顺带修的 bug**：多档规则下 `n_p0` 之前写死成等级 2，三档规则时会把 P1 误计成最高档；改为按规则条数算。
- **⚠️ 公开集的「一次性」提醒**：NAB 已参与过上述修复（推荐列表补次选），**不再是独立的泛化验证集**。项目原则是「公开集只用于泛化验证，不用于调参」，这一点被破坏了。后续重新评估 auto 必须换用未参与调参的公开集。

## 表单即时校验与 Chronos 接入（2026-10-30）

**表单即时校验**（ROADMAP 上列的两项「以后做」）：

- **最小窗口点提示**：任务表单的窗口点数/执行间隔改成后端真实边界（10 ~ 100000 /

  `tests/web/test_api_contract.py` 做前后端交叉校验（改一边就红）。
- **freq 格式校验**：`features/metrics/freq.ts` 的正则与后端 `timeutil.freq_delta`
  一致，指标表单当场拦下非法频率，不再等提交后的后端 400。
- 顺带修掉两个真实缺陷：表单 `handleOk` 里 `validateFields()` 抛出的 promise 没人接
  （浏览器控制台 unhandled rejection）；预览图把**空数组**的基线当成「有基线带」
  （`[] !== null`），会画出空的图例项。

**Chronos 接入平台**：

- 平台注册表加入 `chronos`；`auto` **不会**选中它（形态推荐的候选里没有预训练模型），
  离线评测的默认检测器集合也排除它（否则一次评测从几秒变成十几分钟）。
- 能力探测：catalog 给出 `available` / `reason` / `slow`，前端下拉禁用不可用项，
  建任务时前置 400 拒绝，对比时跳过并说明原因。
- **修掉一个严重缺陷**：运行期必须 `local_files_only=True` —— huggingface.co 不可达时
  `from_pretrained` 会退避重试 **~540 秒**才报错（实测 542 秒 vs 离线 0.05 秒），
  而且每次重启服务都要重付这 9 分钟。Chronos-2 还要绕开 `from_pretrained`
  （它内部的 adapter 检查不接受 `local_files_only`）。
- **默认模型换成 `amazon/chronos-2`**：比 chronos-t5-tiny 快 12 倍（326 vs 4021 ms/序列）
  且 F1 略高（0.210 vs 0.184）。
- **放宽「至少一条倍数条件」的硬约束**：规则表可以只有绝对值条件，此时上下界带用
  检测器自己的惯用阈值，分级仍由规则表决定 —— 这样 Chronos 的 `>=0.5, P1` 才能用。

## 告警中心与删除功能（2026-10-30）

**告警中心**（ROADMAP 上最后一项「以后做」的一层）：

- **只做列表** —— 跨任务汇总告警事件，不做状态机 / 抑制 / 通知
  （那是完整 AIOps 平台的工作量，与本项目的定位不匹配）。
- **一条事件 = 一段连续告警点**：逐点 `severity` 合并成区间，档位取区间内最高档。
- **以每个任务的最新一次运行为准** —— 平台任务是滚动窗口，同一段异常会被
  连续多次运行重复报出；扫全部历史 run 会让同一个异常出现很多遍。
  语义是「当前各任务处于什么告警状态」。
- **告警明细不进数据库** —— 它躺在 run 的 npz 里，由 `platform/alert_events.py`
  在查询期读出聚合。零 schema 变更，老库直接能用。
- **跳过的任务如实报告**：没跑过 / 运行失败 / 运行中 / 结果文件缺失，
  在 `skipped` 里给出原因，不静默消失。
- 前端新增 `/alerts` 页面；空态区分「还没有检测任务」与「当前没有告警」。

**删除功能**：

- 数据库层**早就支持级联**（schema 写了 `ON DELETE CASCADE` +
  `PRAGMA foreign_keys=ON`），这次补的是缺失的端点层。
- 补上数据库管不到的一环：**run 目录文件清理** —— 外键管不了文件系统，
  不清的话 `cache/platform/runs/{run_id}/` 会变成孤儿垃圾。
- **运行中的任务返回 409** —— 复用 runner 的 `_INFLIGHT`（手动触发与调度两种来源都覆盖）。
- 前端三个列表页加删除入口，确认弹窗写明**连带删除的数量**
  （影响范围从 `catalog` 自己算，不另开端点）。

## 前端信息架构重构（2026-10-30）

**从「平铺的只读表格」改成「按职责分层的可操作界面」**：

- **层级从属**：真实关系是 数据源 → 指标 → 序列，平铺成同级页面会丢掉这层关系。
  侧边栏只留一级入口；`/sources/:id` 是指标列表，`/metrics/:id` 是指标详情

- **序列总览页删掉** —— 它展示的是 synthetic 合成序列，与平台侧的数据源/指标无关；
  合成序列在「检测记录」页左栏可选。
- **可编辑**：数据源、指标、检测任务配置都能改（此前只有新建与删除）。
  告警规则仍不可自由编辑（spec §8.3），只能通过「应用反馈建议」按比例缩放。
- **可下钻**：序列总览与告警事件都能点开看图；告警详情高亮本次告警区间。
- **任务详情拆成四个路由**（配置 / 运行记录 / 检测结果 / 人工反馈），
  各分区只发自己需要的数据。
- **评估报告**：加时间筛选、维度聚合（形态 / 算法 / 来源）、删除与恢复检测记录。
  「Bad Case」正名为「检测记录」—— 那一页展示的是一次检测的完整结果，不只是 bad case。

**顺带修掉的真 bug**：

- **时间戳的单位换算** —— numpy 的 `timedelta64[m] → datetime64[ns]` 是**重新解释**
  不是换算，5 分钟被当成 5 纳秒；500 个点塌成一个瞬间，图表 x 轴退化成一条竖线。
  加载时又少了 epoch 基准，真实数据集的时间整体平移。
- **合成数据的时间基准** 从 epoch 挪到 2026-01-01，每条序列按 seed 偏移几天 ——
  之前全挤在 `1970-01-01`，「按时间筛选」根本无从谈起。
- **告警候选值从筛选后的集合汇总** —— 选了 P1 之后下拉里就只剩 P1，筛选器把自己锁死。
- **告警时间筛选靠字符串比较** —— 事件时间是 `...07:23:00`，浏览器给的是
  `...07:23:00.000Z`，字典序一比边界上的事件就漏了。
- **`fields.get(k) or current` 把 0 当成「没传」** —— 非法输入（窗口点 0）被静默忽略。

## 「数据」分组导航、指标独立页与测试告警（2026-11-03）

**导航**：侧边栏「数据源」改成 **「数据」分组**，下面挂「数据源」与「指标」。

- 两者是**从属关系**（指标从某个数据源取数），平铺成一级入口会丢掉这层。
- 分组项本身**不是路由** —— 选中态与页面标题都从展平后的可路由项算。
- 选中的子项所在的分组**自动展开** —— 否则停在「指标」页时侧边栏只看到
  「数据」两个字被高亮，用户会以为自己还在数据源页。

**指标独立成页**：

- 数据源**列表页**不再展示指标（一个页面讲一件事）
- 数据源**详情页**仍然展示该源下的指标（从属关系该有的样子）
- 新增 `/metrics` 列表页，列补齐了时间列 / 值列 / 时区 / 缺失
- 新增 `/metrics/new?source_id=` 与 `/metrics/:id/edit` —— **独立页面，不是弹窗**

⚠️ **为什么不用弹窗**：指标配置要写 SQL、要选列、要预览取回来的数据，
弹窗塞不下；预览要开新标签页时，弹窗会跟着一起消失。

**测试告警**（`POST /api/platform/jobs/{id}/test-run`）：真跑一次检测，
但**不落库、不落盘**。

⚠️ **与真实执行走同一段代码** —— 把 runner 拆成「算」（`_compute_job`）
与「落盘」（`_run_job`）两段，两条路共用前者。
所以「试跑的结果」**就是**「真跑一次的结果」，而不是另一套近似逻辑。
⚠️ 告警点**逐个列出、不抽样** —— 抽样可能正好丢掉告警点，
用户会误以为「没有告警」。
⚠️ 试跑**不占用 `_INFLIGHT`** —— 否则会挡住真正的定时执行：
试一下反而把任务停了。

**顺带修掉的真 bug**：

- **试跑端点的时间戳** —— 结果里存的是 int64 纳秒，直接 `astype("datetime64[s]")`
  会把纳秒当成秒，时间戳变成「五百年后」。
- **指标表单的初值 effect** 会在 catalog 到达时**冲掉用户已经敲的字**。
- **换检测算法时阈值要跟着换** —— 统计型的分数是「几个尺度单位」（阈值 2.5），
  Chronos 的是 [0,1] 的相对越界程度（阈值 0.5）。沿用旧阈值 =
  **告警永远不触发**，而界面显示「一切正常」。这是静默失效，比报错还糟。
  修法：跨量纲族时把阈值换成新算法的默认值（规则表跟着重算），
  同族换算法则不动。

## 连接器层与数据浏览器（2026-11-01）

**连接器层**（`platform/sources/`）：把「取数」与「后处理」拆开。

- 连接器只负责 **SQL → DataFrame**；时间解析 / 排序 / group by 拆分 / 缺失值策略
  **全部共用**（`sources/base.py`，方言无关，只依赖 pandas）——
  换一种数据源 = 新增一个类，不用复制后处理。
- `sources/sqlite.py`（`SqliteConnector`）+ `sources/http_sql.py`（`HttpSqlConnector`）；
  `sources/__init__.py` 是 kind → 类的注册表。`sqlite_source.py` 变**薄壳**
  （只再导出 `load_series`），既有测试与 monkeypatch 目标名零改动。
- **HTTP 透传数据源**（`kind="http"`）：把指标 SQL **原样**发给远端 SQL-over-HTTP 网关
  （InfluxDB 3 的 `/api/v3/query_sql`、ClickHouse 的 `/?query=`、TDengine 的 `/rest/sql`…），
  远端自己执行、只返回结果集，平台不落地也不代算。
- **数据源 config 配置**：`sources` 表新增 `config` JSON 列存 kind 专属参数；
  `kind` 收敛为枚举（`sqlite` / `http`）；凭据脱敏在 store 层（前端永远拿不到明文）。
- **数据浏览器**：`POST /api/platform/sources/{id}/query` —— 在数据源上写只读 SQL，
  看列结构与前 N 行，再一键生成指标。
- **`$timefilter` 由连接器各自渲染**：SQLite 用 `julianday()`（参数绑定），
  HTTP 用按 `time_format` 生成的 ISO 字面量。浏览预览与指标运行时走**同一条路径**，
  所以「预览看到的」必然等于「跑出来的」。
- ⚠️ **安全边界**：SQL 原样发到远端执行，平台的只读校验只是**第二道防线**
  （关键字黑名单可绕过）；真正的边界是**远端账号的权限** —— 必须用只读凭据。

本轮**没做**（都留给后续 spec）：告警外发、认证与多租户、
数据保留与清理、分布式调度。

## 数据保留与清理（2026-11-02）

平台的任务每 5 分钟产生一次运行记录（DB 一行 + 一个 npz 目录）。
实测本机跑了两天：**803 行 runs、14 MB 结果目录**，而且**没有任何东西会清理它们**。
按这个速度一年就是 21 万行、约 4 GB —— 而且「803 条一模一样的运行记录」
在作品集演示时是负分。

- **保留窗口 = 「每任务最近 N 次」∩「最近 T 小时」**（默认 100 次 / 24 小时）。
  ⚠️ 是 ∩ 不是 ∪ —— 用并集的话上界不成立（高频任务会留下远超 N 条）。
  数量上限管磁盘上界，时间上限管低频任务。
- **三条不能破的约束**（破坏任何一条都不是「清理过头」，是**功能坏了**）：
  1. **最新一次运行永远保留** —— 告警中心只读最新 run，删了它整个告警页就空了；
  2. **正在执行的运行不删** —— runner 还在往它的目录写 npz；
  3. **先删文件、再删数据库行** —— 磁盘占用的释放才是主要目标。
- **人工反馈不删** —— 那是人工数据。只把指向已删运行的 `run_id` 置 NULL
  （表里没有外键约束，必须手动 UPDATE）。
- **假远端的数据不归平台管** —— 它在 `data/mock_tsdb/`，自己滚动保留 6 小时。
  路径完全不相交，清理碰不到它。标注、回测侧检测结果同理。
- **触发**：调度器 tick 后**节流**清理（每小时一次，失败只记日志，
  不能把调度线程带走）+ `make prune` 手动 + `POST /api/platform/prune`。
- **看得见**：`GET /api/platform/storage` + 概览页「数据保留」卡片。
  ⚠️ 概览页的「累计运行」因此改成「**保留期运行**」——
  清理后这个数字不再是无界的累计值，叫「累计」就是撒谎。

验证：变异测试确认新测试真能抓到故障（去掉「最新一次保留」→ 4 个测试失败；
去掉「正在执行的不删」→ 2 个失败；反馈改成直接删 → 1 个失败；
数量上限失效 → 2 个失败；孤儿目录不清理 → 1 个失败）。

⚠️ 其中「正在执行的不删」这一条**第一版的测试是白写的** ——
被保护的 run 恰好是「最新一次」，而「最新一次保留」已经挡住了它，
去掉 protected 分支测试照样绿。改成「正在执行的那次不是最新的一次」
（多进程部署时的真实局面）才真正测到了。

真机：803 条真实运行记录清理后剩 200 条（每任务 100 次上限），
磁盘 14 MB → 4.0 MB；告警中心清理后仍有 13 个事件；
人工反馈一条不少、`run_id` 变 NULL；假远端数据与标注原封不动。

本轮**没做**：保留策略的管理界面（参数走环境变量 + CLI）、
按磁盘配额清理、清理历史审计。

## 保留策略简化（2026-11-02，实施后校准）

保留策略原本是**两个维度**：「每任务最近 N 次」**∩**「最近 T 小时」。
反馈指出**太复杂** —— 同意，改成**单一的时间维度**：

| | 原来 | 现在 |
|---|---|---|
| 策略 | 「最近 100 次」∩「最近 24 小时」 | **「最近 180 天」** |
| 环境变量 | `ANOMALY_LAB_RETENTION_HOURS` + `..._MAX_RUNS` | `ANOMALY_LAB_RETENTION_DAYS` |
| CLI | `--hours` + `--max-runs` | `--days` |

为什么该简化：

- **时间维度的保留期是行业惯例**（Prometheus / Grafana Cloud / Datadog 都这么配），
  用户配 180 天就知道会攒多少 —— **可预测**。
- 两个条件取交集意味着要解释「∩」、要测两套边界、文档要多写一段，
  收益却只是**给高频任务兜底**。
- 兜底不该塞进策略里让人去理解 —— 该由**磁盘上限**做。

保留下来的：

- **两条功能性保护**（最新一次永远保留、正在执行的不删）——
  它们不是策略复杂度，是「不能弄坏东西」。
- **磁盘上限兜底**（单任务 4 GB）：保留期永远优先，只有它兜不住才生效。
  触发了会在清理结果里**说出来**（`disk_capped_jobs`），不藏着 ——
  「实际保留期比配置的短」这种事不能让用户以为配 180 天就真是 180 天。

⚠️ 破坏性变更：环境变量名、CLI 参数、`/api/platform/storage` 的 `policy` 结构都变了。
（项目还在 v1，直接换，没有兼容层。）

## 预览页的 Grafana 风格时序图（2026-11-03）

「预览指标数据」页顶部加一张时序图：x 轴是时间，y 轴是**值列**，
有分组列就每组一条线。

**图上画的是「值列」，不是猜的** —— 取角色指派里的值列，
没指派就不画图并说明还差什么（不给空白框让人以为「这个源没数据」）。

### 时间轴坐标由**后端**算

浏览响应加 `time_values`（epoch 毫秒），用
`platform/sources/base.py:parse_time_column()` —— 与**指标运行时同一份逻辑**。

⚠️ 为什么不放前端解析：浏览页的意义就是让用户确认
「我以为的数据」就是「跑出来的数据」。逻辑放两处必然漂移
（`iso_naive` 的源时区、`epoch_s`/`epoch_ms` 的单位最容易错）。

浏览里的解析是**宽松**的（坏值 → 断点 `null`），
指标运行时是**严格**的（坏值 → 任务失败）——
探索不该因为一行坏时间就整个失败；但**绝不画到 1970 年**。

### 顺带修掉的几件事

- **时间列的两个入口没联动**（上一轮已修）：列头下拉指派「时间列」
  不会填「时间列」输入框，而查询请求发的是输入框的值 ——
  用户做了半天，SQL 里写 `$timefilter` 仍然报「需要指定时间列」。
- **`inferRole` 先看 dtype** → **epoch 整数时间列被判成「值列」**，
  `ts` 抢走了值列的角色、真正的 `value` 反而「不使用」，完全反了。
  改成**名字优先**（名字精确匹配 `ts`/`time`/`timestamp`/… 的先判成时间列）。
- **时间列变了不自动重跑** → 用户换了时间列还得手动再点「执行」，
  图停在旧的那一列，看着像「改了没反应」。现在 400ms 去抖自动重跑。

### ECharts 6 的两个坑

- `scale: true` 只表示「不强制含 0」，随后的 nice 取整**仍会把 min 拉回 0**
  （间隔取 20 就正好落在 0）。要真的贴着数据走，得自己算边界。
- `min: 'dataMin'` 会把 `12.0746815396624` 这种原始值直接当刻度标签。
  现在边界自己算：向下/向上取整到 1 位有效数字的台阶。

## 浏览页的几处收拾（2026-11-03）

- **去掉「取数配置」下那段提示** —— 「改 SQL → 执行 → 看结果。列头下拉决定……」
  说的都是界面本身就有的东西，等于没信息。
- **明细列表分页**（单页 20 行）—— 一次取 100 行全摊开，是一屏拉到头的长表。

⚠️ 顺带说清一条容易误解的规则：

- **浏览**时可以不写 `$timefilter`，自己写时间条件也行（只要求只读 + 单语句）。
- **指标**里必须**恰好一个** —— 指标是**滚动窗口**执行的
  （调度器按 `now - freq × window_points` 取窗，`$timefilter` 就是那个边界）。
  写死时间条件 = 窗口永远不滚动，数据会一直是旧的。

## 假远端的多形态数据（2026-11-03）

假远端原来只有 4 条曲线，基线只有 `constant` / `daily` 两种 ——
**没有真正的「趋势型」「阶跃型」「稀疏事件型」**。
（回测侧的合成数据集 `data/synthetic/` 倒是有 6 类形态，
但那两套生成器各写各的，形态逻辑完全不共享。）

现在加了三条形态演示曲线：

| 曲线 | 形态 | 参数 |
|---|---|---|
| `trend-load` | 线性趋势（整条都在涨） | `level=40, slope=0.02` |
| `step-cache` | 水平跳变（每 3 小时切一次） | `level=30, step_period=180, step_delta=25` |
| `job-runs` | 稀疏事件（绝大多数点是 0） | `event_rate=0.012, event_width=2, event_value=25` |

⚠️ **SQL、指标、告警任务都不用改** —— `group_column=series`
在加载层自动把新曲线拆成新序列。演示时一条命令就能看到 7 条序列。

### 两个设计决定

- **阶跃型做成周期性的**（每 3 小时切一次），不是一次性跳变：
  假远端是**持续运行**的，一次性阶跃只发生一次 ——
  演示时早就滚出 6 小时的保留窗口了，**永远看不到「抓住跳变」的那一刻**。
  周期性才能一直演到。
- **稀疏事件保证不重叠**：候选起点若与前面 `event_width` 个点里的候选挨着
  就否决 —— 一串挨着的候选里只有第一个活下来。
  ⚠️ 去重范围是 `width` 个点而不是 `width - 1`：
  起点间隔 `width` 时两个事件仍会首尾相接（连成 2×width 的一段），
  那就不是「宽度 = width」了。**这是实测踩出来的** ——
  第一次写成 `width - 1`，测试直接红。

### 库要重建：序列定义的指纹

db 里存的是**按旧定义造出来的历史数据**。加了新曲线之后，旧库里：
新曲线缺那段历史、各曲线的 index 也可能错位 ——
**这种错位不会报错**，只会让图看起来莫名其妙。

所以库会记下序列定义的**指纹**（`sha256` 前 16 位），对不上就**明确报错**，
让人 `rm -rf data/mock_tsdb/` 重造，而不是静默跑出一堆怪数据。

## 已修复：检测器尺度退化时的静默失效（2026-11-03 发现）

**状态：已完成。** 现在所有尺度型检测器共用 `detectors/scale.py` 的降级链，
结果里明确带 `scale_source` / `scale_fallback` / `status`（见
[ALGORITHMS.md](ALGORITHMS.md) 的「尺度降级链」）；尺度不可判时状态是
`undetermined` 而不是「一切正常」。包括 `theil_sen` 在内的趋势型检测器
也不再自己估残差尺度，死传感器 / 常数序列不会因浮点噪声报出假告警。

> 以下保留当时的排查记录。

`job-runs`（稀疏事件）实测暴露出来的：

```python
# src/anomaly_lab/detectors/statistical.py
scale = np.where(scale > 0, scale, np.nan)   # IQR = 0 → NaN
scores = np.where(np.isfinite(scores), scores, 0.0)   # NaN → 0
```

窗口里 75% 分位数仍是 0 → **IQR = 0** → 分数**算不出来**（除零）→
平台把算不出来的分数**按 0 处理** → 界面显示「一切正常」。

⚠️ 这是**假的「一切正常」** —— 实际是「算不出来」，
数据里明明有 25 的尖峰（相对基线是无穷倍）。与「换算法不换阈值」
是同一类问题：**静默地把「不知道」说成「没事」**。

- `iqr` / `mad` 在稀疏数据上完全失明（实测：`job-runs` 一条都不报）；
- `chronos` 不受影响（分数是 [0,1] 的相对越界程度，不依赖分位数尺度）。

⚠️ 当时没直接改，因为分数的语义改动会牵动「落盘 → JSON → 前端」整条链
（NaN 序列化给前端不是合法 JSON，这也是当初写 `→ 0.0` 的原因）。
后来补上了「无法判定」的第三态（`status="undetermined"`），
分数仍是合法的 0，但状态不再冒充「一切正常」。

## 告警阈值可以改了（2026-11-03）

任务配置页上的「告警规则 P1 × 2.5 / P0 × 3.75」是**只读**的 ——
而 2.5 / 3.75 恰恰是**最该能调的东西**（算法的默认阈值）。

之前不能改的原因不是技术问题，是「spec §8.3 说告警规则不能自由编辑」。
现在改掉了：

- **后端**：`PATCH /api/platform/jobs/{id}` 接受 `alert_rules`；
  `update_job_config` 支持显式规则表，**阈值跟着规则表走**
  （阈值本来就是规则表的快捷视图）。
- **前端**：新组件 `AlertRulesEditor` —— **档位并排**的可编辑控件
  （P1 一组、P0 一组），不是纯文本框。
  绝对值条件（`值 > 50 记 P0`）保留在折叠区里，原有写法不变。
- 任务配置页与新建任务表单都用它。

### 顺带发现并修掉的两件事

- **绝对值条件会被冲掉**：改阈值或换算法时规则表被重算成默认两档，
  用户配的「值 > 50 记 P0」就没了。绝对值条件与量纲无关，
  现在**重算时保留**。
- **档位名与阈值顺序打架**：用户把 P1 的阈值调到比 P0 高，
  按倍数排序后 P0 变成更容易触发的那一档 —— 与「P0 最严重」正好相反。
  现在前端会提示，后端也会拒（倍数必须从小到大、不能重复）。

`InputNumber` 会按 `step` 的小数位**推断精度**（`step={0.25}` → 2 位），
于是 2.5 显示成「2.50」。用 `formatter` 去掉尾零才显示原值。

验证：前端 365 passed（+14）、后端 647 passed（+13）；tsc / build / 合规自检全绿。
浏览器实测：改 P1 → 保存 → 刷新后仍在；后端规则表与阈值同步更新；
档位顺序冲突的提示如期出现。

## 趋势型检测器 + `deseasonalized_iqr` 改名（2026-11-04）

### 起因

问「`/detections?series_id=trending-2057-500&detector=iqr` 是不是有问题」——
趋势型序列为什么用 IQR？

**结论：用户的直觉完全正确**，但机制和他想的不同：

1. `/detections` 是回测侧的**多算法对比页** —— 一条记录是「序列 × 算法」，
   URL 里的 `detector=iqr` 是**对比视图里当前选中的那一列**，不是系统给 trending 选的。
2. 但 iqr 在 trending 上确实**大幅漏报**：合成集 20 条 trending 序列，
   iqr 召回只有 20.2%，去趋势类算法 52%+
   （单条 `trending-2057-500`：iqr Recall 0.250，theil_sen 1.000）。
3. 报告当时**只跑了 iqr 一个算法**（`reports/latest/report.json` 里 120 行），
   所以页面上「只有 iqr」看着像系统选择 —— 其实是没跑别的。

### 新增 `theil_sen`（Theil-Sen 稳健趋势线 + 残差 MAD）

用户设想的第 2、3 步「线性拟合 + 检测出异常点」**已经存在**
（`trend_residual_iqr`，旧名 `deseasonalized_iqr`），
但它是**最小二乘** —— 一次尖峰就能把趋势线拽歪。

新检测器用 **Theil-Sen**（点对斜率的中位数）：

| | `trend_residual_iqr` | `theil_sen` |
|---|---|---|
| 趋势线 | 最小二乘 | Theil-Sen 中位斜率 |
| 抗离群点 | 弱 | 强 |
| 残差尺度 | IQR | MAD×1.4826 |
| 默认阈值 | 2.5 | **3.5**（实测值） |

⚠️ **阈值 3.5 是扫出来的**，不是拍的：k=2.5 精确率只有 73%，k=3.5 是 98.3%
而召回只掉 2.6 个百分点。

⚠️ **估趋势用清洗值、打分用原始值** —— 异常点必须留在残差里。

### 改名 + 旧名别名

`deseasonalized_iqr` 说的是「去季节化」，做的却是「去**趋势**」——
名不副实让人 grep「趋势」都找不到它。

改名 `trend_residual_iqr`，**旧名保留为别名**（`DETECTOR_ALIASES`）：

- 旧名仍能造出检测器、仍判为「可用」、仍能跑；
- 但**下拉清单里只出现新名**（否则用户看到两个一样的选项）；
- 历史评测产物里的旧名要有中文标签 → 前端加了 `lib/detectorLabels.ts`
  （**多带旧名**映射，与后端 `DETECTOR_LABELS` 同源）。

### 顺手修的

- `trend_residual_iqr` 的趋势线改用 `winsorize` 后的值 ——
  原来用原始值做最小二乘，尖峰会拉偏（`stl_residual` 的注释早就承认了这个问题，
  但两个算法没对齐）。
- **`stl_residual` 从 trending 的推荐列表里摘掉** ——
  它在无周期的趋势序列上会**爆掉**：STL 需要一个真实存在的周期，
  而 `detect_period` 对趋势序列会估出伪周期（500 点序列估成 166，即「只有 3 个周期」），
  拿它分解就得到一堆乱残差 → 报出 2032 个点、精确率只有 11.3%。
  它**不是废品**（真周期序列上 F1 0.491，是最好的那个），只是不能用在没有周期的序列上。
- 前端所有显示算法名的地方换成中文标签（检测记录页、评估页、筛选栏、平台侧）。

## 顺带发现的两个问题（**未修**）

### ① `detect_period` 对趋势序列估出伪周期

500 点的 trending 序列 → 估出周期 166（即「只有 3 个周期」）。
刚好卡在 `MIN_SAMPLES_PER_PHASE = 3` 的门槛上过了关。

影响面大：`detect_period` 同时被 `seasonal` / `stl_residual` / 分类器的
`dominant_period` 用着，改它要单独评估。

### ② 假远端 `trend-load` 的形态分类会漂移

同一段趋势数据，随着 6 小时窗口滚动，分类结果在 `trending` 与 `step` 之间跳
（`trend-load` 的 slope=0.02/点 vs sigma=1.2，趋势信号相对噪声偏弱）。

后果：auto 的选型会在 `theil_sen` 与 `trend_residual_iqr` 之间摆（都在趋势族，行为相近，
影响不大），但**分类卡片显示的形态会变**。

修法：把 `trend-load` 的 slope 调大（让趋势更明确），或给分类器加「趋势显著性」的判据。
⚠️ 改曲线定义后必须 `rm -rf data/mock_tsdb/` 重建假远端。

验证：后端 672 passed（+22）、前端 377 passed（+2）；tsc / build / 合规自检全绿。
浏览器实测：检测记录页 4 列算法、标签中文、theil_sen 在 trending-2057-500 上 Recall 1.000。

## 同族换算法时的阈值继承（2026-11-04，追加）

新增 `theil_sen` 时撞上了一个**既有设计**的盲点。

### 现象

把任务从 `iqr` 换成 `theil_sen`，阈值**没变**（2.5 / 3.75）——
而 `theil_sen` 的惯用阈值是 **3.5**（实测出来的）。
k=2.5 时精确率只有 73%，k=3.5 是 98.3%。

### 根因

`update_job_config` 里的规则是「**跨**量纲族才换阈值」，
同族换算法沿用旧阈值 —— 理由是「用户调好的 2.5 在 mad 下依然有意义」。

⚠️ 但它**分不清**两件事：

| | 该不该沿用 |
|---|---|
| 用户**特意**把 mad 的阈值调成 2.5（要更灵敏） | 该沿用 |
| 用户**从没动过**，用的就是 iqr 的默认值 2.5 | 不该沿用 —— 新算法的惯用阈值是 3.5 |

后者是「继承来的默认值」，沿用它等于**默默给用户一个次优配置**，
而界面上一点提示都没有。

### 修法

判据改成：**两个阈值都恰好等于旧算法的默认值**时，
认定它是继承来的 → 按新算法重设；只要用户动过其中一个，就保留。

⚠️ `auto` 不在注册表里（运行时才落到具体算法），
所以取默认值要走 `detector_default_threshold()`（`auto` → 兜底算法）。

### 前端配套

算法下拉里**显示每个算法的惯用阈值**：

```
稳健趋势线 Theil-Sen（惯用 3.5）
```

用户换算法时就知道该把阈值调成多少，不用猜。

## v3 候选：指标预检实验台（Lab，2026-11-04 立项讨论）

**定位**：指标在真正建检测任务**之前**，先取一段真实数据做完整预检——
形态推断 → 多算法检测 → 效果分析 → 满意了再一键建任务。
详见 [LAB.md](LAB.md)。

**为什么需要**：

- 现有链路是「数据源 → 指标 → 检测任务」，缺了「**这个指标到底能不能上检测**」这一步。
- 现在 `auto` 的形态推断只在建完任务、跑完 run 之后才发生，结果埋在产物里；
  用户无法在"建任务之前"看到推断是否合理、哪个算法更稳。
- 现有 `试跑 / 多算法对比` 都**要求任务已存在**，对新指标是倒序的。

**范围（P0/P1 为核心）**：

- P0：数据切片（数据源 SQL / 已有指标）+ 跨时间窗采样 + 质量体检 + 形态推断
- P1：多算法检测 + 图表 + 无真值画像（检出画像 / 倍数敏感性 / 跨窗稳定性）
- P2：实验记录（spec + env + result，可复现）+ 一键建任务
- P3：有真值模式（合成 / 公开集 / 人工标注 → F1，校准/测试分开）
- P4：`transform` / `postprocess` 插槽（有 3 个真实用例再做）

**关键设计决定**：

- **数据采样**：默认最近 30 天 / 每条序列 10k 点预算 / 窗口与生产同构
  （`window_points` + `freq` + `missing_policy` 必须与任务一致）；
  首选「一次拉整段 + 本地切窗」，超限才退化为按窗口分页。
- **无真值是主场景**：产出是"证据 + 取舍"（质量体检 / 检出画像 / 稳定性 /
  倍数敏感性），不是 F1；不假装有真值。
- **形态是推断，不是配置**：`classify()` 今天就能对任意序列给 6 类之一，
  不需要开放 `MetricClass`；lab 只补"建任务前可见 + 可覆盖算法"。
- **不做**：动态 import / 插件沙箱、DAG 引擎、自动改写指标 SQL、
  把实验产物写进基准报告。
- **复用**：临时 `Metric`（id=-1）+ `series_from_frame`，保证
  「实验里看到的 = 上线后拿到的」；抽出无 job 的 `run_detectors()` 供 lab 与 job 共用。
- **产物隔离**：`data/lab/experiments/`，永不写入 `reports/latest/`。

**开放项**：

- [ ] 采样默认值（30 天 / 10k 点 / 100 窗）是否合适
- [ ] `stratified` 粗扫指标是否够用
- [ ] 分组指标默认纳入多少条序列（`max_series = 20`）
- [ ] 实验记录只落盘 JSON，还是也进 SQLite
- [ ] 人工标注升级为真值的入口（实验详情页 vs `/annotate`）

**P0 落地时的实测发现**（值得留给 P1 参考）：

- **时间范围默认「最近 30 天」很容易大半窗口是空的** —— 用户选的范围常常远大于数据实际覆盖区间，
  切出来的窗口大半没数据，纯浪费预算。P0 的对策是**如实报出数据实际覆盖区间**
  （`series[].data_start` / `data_end`）+ 明确警告；P1 应考虑**按数据实际跨度自动收窄采样范围**。
- **形态推断按窗口投票比按序列投票更可靠** —— 分组指标有 20 条序列时，按序列投票会让单条序列主导结论。
- 窗口点数必须与任务一致：500 点 @5min 只有 1.7 天，**看不到日周期**（需 864 点）——
  周期可识别性检查（`period_capability`）必须在选算法前就给出来。

**P1（多算法实验）的实测结论** —— 值得记住：

- **光看「检出量」会选错算法**。demo 数据 4 窗上：`stl_residual` 检出 26%（最多），
  但倍数从 1.5× 调到 4.0× 只从 299 降到 179 —— **阈值调它没用**（残差比例与 z 分数不同量纲），
  而且慢 100 倍；反过来 `iqr` 极稳（离散度 0.0022）却几乎不报（1/800）—— **稳而无用**。
- **`auto` 逐窗混用算法比任一固定算法更鲁棒**：它在同一批窗口里用了
  季节性分组×2 + IQR 围栏×2，检出量随倍数变化**最平缓**。
  这说明「每窗各选一个」值得做，不只是形式上的花活。
- **倍数敏感性零额外算力**：分数只算一次，换一套告警规则表重判等级即可 ——
  这让「阈值好不好调」变成可以便宜地测出来的东西，而不是上线后才发现。

**P2（实验记录 + 一键建任务）的落地结论**：

- **指纹必须剔除耗时** —— `elapsed_ms` 每次都不同，它不参与「两次结果是否一致」的判定。
  剔除后同一 spec 跑两次指纹一致，这条验收才能自动化。
- **记录的是「屏幕上看到的那份结果」，后端不重跑** —— 重跑会因数据源变化与屏幕对不上，
  用户会以为记录不可信。真要复现，用记录里的 spec + env 再跑一遍。
- **草稿只回填、不创建** —— 建任务这一步仍然由人点确认。
  草稿把实验结论（推荐算法 + 依据 + 窗口点数）搬到表单里，人只做判断。
- **`auto` 是草稿的默认推荐** —— 它逐窗自适应，实测随阈值变化最平缓；
  备选算法列在 `alternatives` 里让人自己挑，不替人决定。

## ⚠️ 一个环境坑：vite proxy 指向 :8000，不是 :8899

`frontend/vite.config.ts` 里 `API_TARGET` 默认是 `http://127.0.0.1:8000`，
而 `make serve` 的 `PORT` 默认也是 8000。

⚠️ **所以改完后端代码后，重启 :8899 是不够的** ——
   浏览器实测打的还是 :8000 上那个旧进程（可能跑着昨天的代码）。

本轮就踩了：重启 8899 后 curl `/api/platform/catalog` 看到新算法清单，
但浏览器里的下拉还是旧的（`deseasonalized_iqr`）。

排查方法：`ss -lptn | grep :8000` 看是不是另一个进程，
以及 `ps -o lstart -p <pid>` 看它什么时候起的。
