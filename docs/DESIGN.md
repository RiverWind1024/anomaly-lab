## 1. 背景与目标

### 1.1 为什么做这个项目

在现职工作中，我参与了「智能异常检测平台」的建设，接触的是**平台侧**（数据接入、配置页面、规则执行、告警联动、评估页面）与**算法侧**（指标自动分类 → 算法适配 → 检测 → 标注 / bad case 回测 → 评估 → 反馈抑制）的接口。

两个具体缺口驱动了这个项目：

1. **深度时序模型是"调用"而非"自持"** —— 统计方法（IQR / MAD / 长短周期联合判断）由我实现，但深度时序模型（Chronos）由其他团队维护，我只在服务接口层面使用，**没有自己部署、训练、评估过**。这导致我能用，但说不清"为什么用它、什么时候不该用"。
2. **根因分析那条线上没有离线评测集** —— 我在异常检测平台做过标注 / bad case 回测 / 评估闭环，但**评估方法论没有在一个可自由实验的环境里从零打通**。缺少"改一次算法 → 量化看到变化"的完整回路。

### 1.2 目标（按优先级）

| # | 目标 | 可验证标志 |
|---|---|---|
| G1 | **打通"全流程"认知**：从数据形态 → 算法选型 → 检测 → 评估 → 迭代，每一环都能自己实现并解释 | README 中有一份端到端流程说明 + 一条命令可跑通全流程 |
| G2 | **自己跑通并评估深度时序模型**，能对比"统计法 vs 自训深度模型 vs 预训练模型"在同一批数据上的真实差异 | 评测报告含三者的对照表（含延迟、显存、参数量、指标） |
| G3 | **实现指标形态分类 → 算法推荐**这套方法论（现职工作里最有价值、也最难被替代的部分） | 合成 6 类形态上的分类准确率 ≥ 90% |
| G4 | **建立"改一次 → 量化对比"的回归评测闭环** | 每次算法/参数/分类规则变更产出一份可 diff 的回归报告 |
| G5 | 顺带补齐 **Python 工程能力**（时序生态在 Python，这是唯一合理选择） | 包可 `pip install`，测试可跑，CLI/文档齐备 |

> **G5 是副产品不是主目标。** 选择 Python 是因为时序检测的生态、教程、论文复现全在 Python 侧，硬用 Java 只会让学习效率腰斩。

### 1.3 非目标（明确不做）

- **不做** 分布式、微服务、消息队列、K8s、CI/CD 流水线（个人学习项目的复杂度陷阱）
- **不做** 在线 / 流式检测（v1 只做离线批量；数据流接口在 v2 预留）

### 1.4 合规红线（不可越过）

> **绝对禁止：现职公司的任何内部数据、内部代码、内部文档、内部告警规则、内部指标口径。**
>
> 本项目只使用：**自建合成数据** + **公开数据集**（UCR / 公开基准）+ **公开实现**（statsmodels / sklearn / PyTorch / chronos-forecasting）。
> 项目不模仿现职系统的内部架构命名，不复用任何内部接口协议，不使用内部截图/文档作为示例。
> 这既是合规红线，也是"能开源"的前提。

## 3. 架构

### 3.1 分层图

```
┌──────────────────────────────────────────────────────────────────┐
│ L5 交付层                                                          │
│   Web 标注页 / Web 评估页  │  CLI（7 个子命令）  │  报告生成器        │
│   FastAPI(JSON API) + 独立 React 前端工程                            │
├──────────────────────────────────────────────────────────────────┤
│ L4 评估闭环层  ★ 本项目的心脏                                      │
│   AnnotationStore(JSONL) → Backtester → Metrics(P/R/F1/延迟)       │
│   → BadCaseAnalyzer(误报/漏报归因) → RegressionReport(版本化对比)   │
│   → ThresholdSuggester(按形态给阈值建议)                            │
├──────────────────────────────────────────────────────────────────┤
│ L3 检测算法层（统一接口，可插拔）                                   │
│   Detector Protocol: fit() / score() / score_type()                │
│   ├ 统计基线: IQR · MAD · 3σ · Z-score · STL残差 · 季节性感知阈值    │
│   ├ 自训深度: TCN · LSTM(+ 变点感知)                                │
│   └ 预训练:   Chronos (本地部署, Apache-2.0)                        │
├──────────────────────────────────────────────────────────────────┤
│ L2 形态分类层 ★ 最有价值、最难被替代                                 │
│   MetricClassifier: 特征提取 → 6 类判别 → Recommendation(算法候选+参数域) │
├──────────────────────────────────────────────────────────────────┤
│ L1 数据层                                                        │
│   SyntheticGenerator(6 形态 × 异常注入, seed 可复现)                 │
│   PublicDatasetLoader(UCR 等, 惰性下载 + 缓存 + 镜像)                │
│   统一契约: SeriesBundle(values, timestamps, freq, masks, meta)     │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 分层原则

- **每层单一职责，层间只通过明确定义的数据契约通信**（`SeriesBundle` 进，`DetectionResult` 出）。
- **L3 只依赖 L1 的数据契约，不依赖 L4**；L4 依赖 L3 的**接口**而非具体实现 → 加新算法不改编排层。
- **L2 是一等公民，不是脚本**：分类结果（形态 + 推荐算法 + 参数域）是评估报告的**分组维度**，也是"算法选型"叙事的载体。
- 换检测器不需要改编排层、评估层、CLI、Web（依赖倒置）。

### 3.3 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **统一分数语义**：`score()` 必须返回 `score_type ∈ {zscore, pvalue, residual_ratio, prob}`，评估层**按语义分桶**做阈值搜索 | 时序检测库最大的坑是各算法分数语义不同（z-score vs p 值 vs 重建误差），不统一就没法公平对比。这个设计本身是"懂行"的信号 |
| D2 | **形态分类 → 推荐算法**作为可测模块，带自己的准确率指标 | 现职工作里最独特、最难被替代的经验；也直接对应"指标形态差异大 → 传统阈值维护成本高"这个真实痛点 |
| D3 | **三种标注来源统一**：`ground_truth`（合成注入）/ `public_label`（UCR 标注）/ `human`（Web 标注） | 评估器需同时支持"有真值"和"只有人工标注"两种模式，后者需要用**区间重叠**（如 point-adjusted / IoU）而非点匹配 |
| D4 | **回归报告版本化**（每次运行产出 JSON + Markdown，字段对齐可 diff） | 直接对应"改一次 → 量化看到变化"的闭环；也是简历上"自动化回归评测"能落地的载体 |
| D5 | **合成数据优先**（形态可控、异常位置已知），公开集做泛化验证 | 分类逻辑和算法适配只有在"形态可控 + 真值已知"时才能被定量验证；公开集形态不可控 |
| D6 | **无网络也能跑通主流程**（合成 + 统计基线） | 实测下载源仅 10 KB/s 且 GitHub/HF 时通时不通。合成 + 统计基线 100% 离线 → 学习不被网络绑架 |
| D7 | **不做数据库**，用 SQLite + JSONL 文件 | 个人项目引入数据库服务是复杂度陷阱；标注用 JSONL 便于 git diff 与人工审阅 |
| D8 | **前后端分离**：独立前端工程（React 18 + TypeScript + Vite + AntD），后端只出 JSON API，构建产物由 FastAPI 托管 | v1 的理由是"只需波形 + 刷选 + 表格"，但实际做下来 4 个页面共 20+ 交互状态（加载/空/错误/数据不足 × 多页），手写命令式 DOM 已不可维护。分离后：**后端不返 HTML**、前端能独立跑测试与构建、AntD 提供一致的交互与无障碍基线 |

### 3.4 数据契约

```python
@dataclass(frozen=True)
class SeriesBundle:
    """贯穿全流程的唯一数据契约（L1 出，L2/L3/L4 都用它）"""
    series_id: str
    values: np.ndarray          # (T,) float64，缺失用 NaN 表示
    timestamps: np.ndarray      # (T,) datetime64[ns]
    freq: str                   # 频率，如 "5min" / "1h"
    labels: np.ndarray | None   # (T,) int8 ∈ {0,1}，异常区间 mask（可空）
    label_source: Literal["synthetic", "public", "human", "none"]
    meta: dict                  # 形态标签、seed、来源、注入参数等

@dataclass(frozen=True)
class DetectionResult:
    series_id: str
    scores: np.ndarray          # (T,) 异常分数
    score_type: str             # D1：语义标识
    is_anomaly: np.ndarray      # (T,) bool，按阈值二值化
    threshold: float
    detector: str
    elapsed_ms: float
```

## 4. 算法清单

### 4.1 统计基线（L3，全部自己实现，不用现成库）

| 算法 | 适用形态 | 关键点 |
|---|---|---|
| IQR | 平稳、无明显周期 | 分位数法，抗离群 |
| MAD | 平稳、尖峰多 | 中位数绝对偏差，对离群更鲁棒 |
| 3σ / Z-score | 近似平稳 | 最朴素基线，用于对照 |
| STL 残差 | 有趋势 + 周期 | statsmodels `STL`，残差上做阈值；**周期长度需由形态分类给出** |
| 季节性感知阈值 | 强周期 | 按"同一时刻跨周期"分组统计（如每小时 24 点位） |
| 变点检测 | 阶梯 / 漂移 | 窗口内均值突变检测（CUSUM / 二分分割） |

### 4.2 自训深度模型（L3，PyTorch，CPU 可跑）

| 模型 | 规模 | 训练数据 | 目的 |
|---|---|---|---|
| TCN | ~0.1–0.5M 参数 | 合成训练集 | 卷积 + 膨胀因果卷积，时序异常检测常用强基线 |
| LSTM + 变点感知 | ~0.3–1M 参数 | 合成训练集 | 与 TCN 对比"递归 vs 卷积"的差异 |

> 训练集用**合成数据**（含正常段 + 异常段），评估在**留出的合成集 + 公开集**上做 → 避免自评自。

### 4.3 预训练模型（L3）

| 模型 | 版本 | 许可 | 备注 |
|---|---|---|---|
| Chronos | `chronos-forecasting` 2.3.2（PyPI 已确认） | **Apache-2.0** | `chronos-t5-tiny` 最小；本地推理。**权重从 HF 下载，时通时不通 → 必须有降级路径** |

**降级策略**：权重不可用时，`compare` 命令自动跳过 Chronos 并在报告中标注"skipped: model weights unavailable"，**不阻塞**主流程。

### 4.4 形态分类（L2）

6 类形态 + 判别特征：

| 形态 | 判别特征（建议） | 推荐算法 |
|---|---|---|
| 平稳平稳型 | ADF 检验平稳、低方差、低自相关 | IQR / MAD / 3σ |
| 周期型 | 自相关峰显著、周期长度可辨识 | 季节性感知阈值 / STL 残差 |
| 趋势型 | 强趋势项、ADF 拒绝平稳 | 去趋势 + 残差阈值 |
| 阶梯型 | 水平突变、均值阶跃 | 变点检测 |
| 高零值比例 | 零值占比高、取值稀疏 | IQR（零值单独建模）/ 泊松型分位数 |
| 稀疏事件型 | 非零样本极少、事件成簇 | 事件计数 + 泊松/超几何检验 |

> 分类器实现：先用**规则 + 统计检验**（ADF / ACF / 零值占比 / 变点统计量）做可解释判别；再讨论是否加 ML 分类器（v2）。
> **可解释性优先于准确率** —— 这是现职工作里选型的实际需求（能向人解释为什么用这个算法）。

## 5. 数据

### 5.1 合成数据（L1，自建）

- 6 种基础形态（对应 §4.4）× 3 种噪声水平 × 多种异常注入：
  - 点异常（spike）、上下文异常（contextual）、趋势漂移（drift）、周期性破坏（frequency/amplitude shift）、方差变化、扁平化（flatline）
- **异常位置与类型完全已知** → 真值精确
- 全部带 `seed` → **完全可复现**（回归对比的前提）
- 输出规模建议：6 形态 × 20 序列 = 120 条训练序列；另生成 30 条留出集

### 5.2 公开数据集（L1，外部）

实测可达性（2026-10-28）：

| 数据集 | 源 | 可达性 | 备注 |
|---|---|---|---|
| **UCR Anomaly Archive 2021** | `www.cs.ucr.edu/~eamonn/time_series_data_2018/` | ✅ **HTTP 206，zip 正常** | 250+ 真实单变量序列，**带异常区间标注** —— 本项目公开集主力 |
| Zenodo | `zenodo.org` | ✅ HTTP 200 | 通用镜像/备份源 |
| NAB | `raw.githubusercontent.com/numenta/NAB` | ❌ 超时 | 备选，需镜像 |
| HF datasets | `huggingface.co` | ⚠️ 时通时不通 | 备选 |
| GitHub raw | — | ❌ 超时 | 不可依赖 |

**下载策略（关键）**：
- **实测速度仅 ~10 KB/s** → **绝不拉全量 zip**（UCR 全量数百 MB，按此速度不可行）
- 实现**按序列惰性下载**：只取用到的少数序列（如 20–40 条），单文件级 URL + 断点续传
- 本地缓存目录 `.cache/datasets/`，记录来源 URL + 校验值，**可断点续传、可离线复用**
- 提供**多镜像 + 手动指定本地文件**两条兜底路径
- 公开集只做"泛化验证"（"算法在真实分布上还活着吗"），**不用于调参**（避免过拟合公开集）

## 6. Web 端设计

### 6.1 标注页

- 左：时序波形（ECharts）+ 缩略导航条
- 操作：**拖拽刷选**一段区间 → 弹窗选异常类型 → 保存
- 右侧：已标注区间列表（可删改）
- 支持逐点标注（spike）与区间标注
- 保存：追加写入 `data/annotations/<series_id>.jsonl`（git 可 diff）

### 6.2 评估页

- 顶部：选择数据集 / 形态 / 算法组合 → 触发批评估
- 主体：**分组指标表**（按形态 × 算法：精确率 / 召回率 / F1 / 延迟）
- Bad Case 列表：点开看**波形 + 分数曲线 + 阈值线 + 人工标注**叠在一起 → **这是"归因"的界面**
- 版本对比：选两个回归报告 → 并排 diff 指标变化

### 6.3 技术约束

- FastAPI（只提供 JSON API，不返 HTML 页面）
- **前端：独立工程** —— React 18 + TypeScript + Vite + Ant Design v5 + TanStack Query + react-router-dom + ECharts
- 构建产物 `frontend/dist` 由 FastAPI 托管（SPA fallback 走 `index.html`）
- 开发期用 vite proxy 把 `/api` 转发到后端，**不引 CORS**
- 后台任务用 `BackgroundTasks` 或简单线程池（无需 Celery）
- Web 只做只读 + 写 JSONL，**不做用户体系/权限**

### 6.4 界面文字规范

⚠️ **不要用一行灰色小字去解释界面。**

那种「字段下面挂一行 `extra`」「面板标题下面挂一句说明」的做法有两个问题：
一是把表单撑得很高却大部分人根本不读；二是**真正会因此做错事的说明被淹没在噪音里**。

所以文字按性质分流：

| 性质 | 去处 |
|---|---|
| 能用界面本身表达的 | **让界面表达** —— placeholder 写格式、label 标「可选」、控件自己钳制上下限、输入时当场校验 |
| 会让人做错事的（写错就整个功能失效） | label 旁的 **ⓘ Tooltip**（`components/FieldHint.tsx` 的 `hint()`）—— 悬停才看得到，但不占空间 |
| 概念解释（「倍数怎么算」「反馈用来做什么」） | 折进 `<details>`，默认收起 |
| 方法论、原则（「窗口点数必须与任务一致」） | **写进文档**（本文件 / `docs/LAB.md`），界面不重复 |
| 统计摘要（「3 个指标 · 5 个任务」） | 保留 —— 那是**信息**，不是说明 |

配套约定：

- ⚠️ antd 的 `requiredMark="optional"` 已经会给非必填项标「(可选)」——
  **别再手写一遍**，会出现「分组列（可选） (可选)」。
- 错误提示、冲突警告、空态文案**照常显示** —— 那些是当下要处理的事，不是说明书。
- 悬停提示（`title=` / `Tooltip`）是安全的，不占版面，可以放心用。

## 8. 里程碑与工期

> 估 **16–20 个工作日**（约 3–4 周），按"每天 2–3 小时有效投入"折算。若时间紧张，按 §8.2 的取舍顺序砍。

### 8.1 里程碑

| 里程碑 | 内容 | 工期 | 验收（可执行命令） |
|---|---|---|---|
| **M0** 骨架 | 包结构、`SeriesBundle` 契约、配置、pytest 骨架、CI 无关的 `make` 入口 | 1–2 天 | `pip install -e .` 通过；`pytest` 空跑通过 |
| **M1** 数据层 | 合成生成器（6 形态 + 6 类异常注入，seed 可复现） | 2–3 天 | `anomaly-lab generate --n 120 --seed 42` 产出数据；两次生成 hash 一致 |
| **M2** 形态分类 | 特征提取 + 6 类判别 + 推荐算法 + 分类准确率评估 | 3 天 | `anomaly-lab classify --eval` 给出分类准确率（目标 ≥90%）；每类给出可解释理由 |
| **M3** 统计基线 | 6 种统计检测器 + 统一 `Detector` 接口 + 阈值搜索 | 3–4 天 | `anomaly-lab detect --detector iqr` 全量跑通；分数语义标注正确 |
| **M4** 评估闭环 | 标注格式 + 回测器 + 指标（3 种标注来源）+ Bad Case 归因 + 回归报告 | 4 天 | `anomaly-lab evaluate` 出 JSON+MD 报告；改阈值后再跑能 diff 出变化 |
| **M5** 深度模型 | TCN / LSTM 自训 + Chronos 本地部署 + 三方公平对比框架 | 4–5 天 | `anomaly-lab compare` 出三方对照表（含延迟/参数量） |
| **M6** Web | 标注页 + 评估页 | 3–4 天 | 能完成"标注 → 重评估 → 看 Bad Case"的完整人工回路 |
| **M7** 文档收尾 | README（架构图/快速开始/评测结果/迭代案例）+ 算法说明 + 数据说明 + LICENSE | 2–3 天 | 陌生人 10 分钟内能 clone 并跑出第一份报告 |

**M7 的"迭代案例"是最值钱的一环**：README 里放一个真实故事 —— v1 在周期型指标上误报率高 → 归因（分数语义/周期长度估计错）→ 改（形态分类给出正确周期长度）→ 回归对比 → 指标变化 X%。这让 README 不只是"能跑"，而是"有方法论"。

### 8.2 时间不够时的取舍顺序

**先砍 M6（Web）→ 再砍 M5 的 Chronos（保留自训模型）→ 再砍 M2 的推荐规则（保留分类）→ 绝不砍 M1 / M3 / M4。**

理由：
- **M1 + M3 + M4 是"全流程认知"的最小闭环**（数据 → 检测 → 评估 → 迭代），砍掉任一环，学习目标 G1 就不成立
- **M2 是最有辨识度的差异化**（对应现职最难被替代的经验），优先级高于 M5 的预训练模型
- **M5 的 Chronos 部分可延后**：统计 vs 自训深度的对比已足够说明问题，Chronos 是加分项
- **M6 Web 可延后**：标注可先用 JSONL 手工编辑完成，Web 只是效率提升

### 8.3 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 公开集下载太慢（实测 10 KB/s） | 高 | M4 无法用公开集验证 | 惰性单文件下载 + 多镜像 + **主流程不依赖公开集**（合成即可完成 M0–M5） |
| Chronos 权重下载失败（HF 时通时不通） | 中 | M5 缺一方对比 | 自动降级跳过 + 报告标注 skipped；`t5-tiny` 体积小，重试即可 |
| Python 3.12 环境装不上（网络） | 中 | 全项目阻塞 | `uv` 可换镜像源；系统 Python 3.14 已有 numpy/pandas/scipy/sklearn/torch/fastapi，作为**兜底**（statsmodels 用手写替代或跳过 STL） |
| CPU 训练 TCN 太慢 | 低 | M5 延期 | 合成数据小（120×~500 点）+ 模型 ~0.2M 参数 + 16 核；先做 10 epoch 试跑再决定 |
| 范围蔓延（想加在线/流式/告警联动） | **高** | 项目烂尾 | §1.3 非目标写死；新想法记入 `docs/ROADMAP.md`，不插队 |

| 合成数据形态不真实，结论不可迁移 | 中 | 学习价值打折 | M5 阶段用公开集做泛化验证；README 明确标注"合成数据结论 ≠ 真实分布" |

## 13. 原始设想与落实对照

> 本节保留**项目发起时写下的原始设想**（`docs/my-thought.md`），
> 逐条标注它在当前实现里的落点。目的是让「想到的」和「做出来的」能对账，
> 避免设想悄悄漂移、或反过来被当成已实现。

### 13.1 架构设想：模块可分离、可插拔

原始设想：核心检测引擎是一个模块、数据加载是另一个、预处理再一个，
**因为大量数据清洗与聚合计算内存压力大，单独服务有利于资源隔离、避免 OOM**；
展示放在前端服务。

落实：**已实现，且比设想更进一步** —— 不是「独立服务」，而是**分层单向依赖**：

```
L1 数据 → L2 形态分类 → L3 检测器 → L4 评估闭环 → L5 CLI/Web
```

层间只走 `SeriesBundle` / `DetectionResult` 两个契约。预处理（清洗、去噪、
聚合）已在 `data/loader.py` 与各检测器的 `estimate_values()` 里**分离**
—— 关键约定：**打分用原始值，估计用清洗值**（单向），否则异常点会把自己洗掉。

> ⚠️ 独立成「服务」（独立进程 / 独立部署）**未做** —— 那需要 RPC 协议与契约版本管理，
> 收益不匹配当前规模。隔离的是**内存生命周期**（分层 + 流式读），
> 不是**进程边界**。

### 13.2 数据源设想：多数据源

原始设想：InfluxDB、Prometheus，甚至 CAT 数据 API。

落实：**多数据源已实现**（`platform/` 层的 source / metric / job 三段式：
数据源 → SQL 指标 → 检测任务），支持 SQL 型数据源 + 本地文件 + 合成数据。

> 🚫 **CAT API 不接** —— 它是现职公司的内部数据接口，属于**合规红线**
> （见 §1.4），本项目不碰。
>
> 另：设计文档 v2 里提过 Prometheus / OpenTelemetry，也**同样不接** ——
> 理由不是技术做不到，而是「接入真实监控体系」会让「独立学习项目」这个前提
> 变得不干净，简历上也说不清楚（见 §11 的措辞纪律）。

### 13.3 算法设想：基线可视化 + 双向 + 未来预测

原始设想：① 算法能给出基线并可视化，超出就告警 ② 部分算法双向（偏高偏低都算异常）
③ 部分算法能给出未来预测值。

落实：**三条全部实现，且带语义被显式区分**：

| 设想 | 落点 | 状态 |
|---|---|---|
| ① 基线可视化 | `Bands`（baseline / lower / upper）→ `DetectionResult` → 前端画带 | ✅ |
| ② 双向异常 | 所有检测器用 `abs` 偏离（`MADDetector` / `IQRDetector` / `ZScoreDetector` / 周期检测器） | ✅ |
| ③ 未来预测 | Chronos 预测区间 + TCN/LSTM 重构值；`Bands.kind = "prediction_interval"` 标记「这是预测区间，不是告警边界」 | ✅ |

> ⚠️ ①②③ 混在一起会误导 —— 统计型检测器的带边界**就是**告警阈值（`alert_boundary`），
> 预测型检测器的带是**模型自己的置信区间**（`prediction_interval`），
> 两者画法相同、含义不同，`kind` 字段就是为此存在的。

### 13.4 批处理设想：批量 + GPU

原始设想：某些算法应支持一次性对多序列批量运算以利用 GPU。

落实：**部分实现**。

- ✅ 深度模型训练是**批量**的（`_windows()` 切窗 + `torch.stack`，一次前向多窗口）
- ✅ 单机多核并行：16 核用 `joblib` 即可（DESIGN §2.2 已列为 v2）
- ❌ **GPU 加速未做** —— 当前是 `torch 2.15.0+cpu`，纯 CPU 训练。
  迁移成本主要在：`torch.set_num_threads(2)` 的线程设置、模型保存的 device、
  以及 batch 切分策略。**先在 CPU 上把评估闭环跑通**是刻意的取舍。

### 13.5 指标形态分类设想：软分类 vs 硬标签

原始设想（这条判断最准）：传统统计分类覆盖不了生产里的奇怪形态；
深度学习分类依赖标注数据；**最大的问题是有些指标本来就是模糊的** ——
「一天内有规律波动但幅度小」，叫它周期型对，叫它平稳型也有道理，
两种算法都能检出异常。

落实：**已识别为「分类器的软推荐未做」** —— 当前 `metric_class` 仍是**硬标签**，
算法推荐按标签查表。

设计的方向（未实现）：分类器输出**候选形态 + 置信度**，
推荐算法时**同时给出「按周期型算」和「按平稳型算」两套结果**，
让人来选 —— 而不是替人决定。⚠️ 这条会牵动整个推荐链路，属于 v2。

### 13.6 检测落地的五个坑

原始设想列了 5 条，逐条落实：

| # | 坑 | 落实 |
|---|---|---|
| 1 | 偏离基准 ≠ 业务异常，用户不买账 → 用**缩放因子**控制敏感度 | ✅ `AlertRule.multiplier`（倍数条件）+ `op/value`（绝对值条件）；前端可调 |
| 2 | 异常程度 → 业务等级的映射难自动生成，依赖用户配置 | ✅ 规则表**顺序即档位**，多条命中取最高档；`severity_from_conditions()` |
| 3 | 每条序列要有标识符，便于按序列/类型/数据源观察 | ✅ `series_id` + `meta.group` + `series.meta`；平台层按 source/metric/job 三段索引 |
| 4 | `group by` 的拆分放哪：查询后拆 vs 检测时拆 | ✅ **查询后拆**（数据加载模块拆成独立序列），与设想一致 |
| 5 | 反序列化 JSON 很吃内存，要注意 | ⚠️ 部分实现：平台层用 **SQLite + npz**（不存 JSON 明文）避免反序列化开销；但**批量内存隔离未做**（见 13.1） |

### 13.7 监控设想：OpenTelemetry

原始设想：考虑用 OTel 做监控，思路不清晰（探针采集 → 上报另一监控服务？）。

落实：**未做**。理由：① 思路本身未清晰；② 引入采集探针会牵扯真实环境，
触碰 §1.4 红线边界；③ 本项目是「检测算法 + 评估闭环」，不是「采集系统」。
记录在 `docs/ROADMAP.md`，不定为 v1 目标。

### 13.8 效果统计与分析

原始设想：TP/FP/acc/recall/F1 评价；分层采样逐条人工算指标不是好方法；
Bad Case 应归档用于未来训练测试。

落实：**全部实现**，且是把「人工逐条看」换成了「自动归因」：

- ✅ 指标：精确率 / 召回 / F1 / 延迟 —— `evaluation/metrics.py`
- ✅ 标注来源：合成（`label_source="synthetic"`）/ 人工 JSONL（`"human"`）/ 公开集（`"public"`）
- ✅ **Bad Case 自动归因**：`evaluation/badcases.py` 按「形态 / 位置（首10%、中段、尾部）/ 连续段还是孤立点」分组，
  不再需要人工逐条统计
- ✅ Bad Case 归档 + **排除清单**（`ExclusionStore`）—— 人工判定的误报可标记为「排除」，
  从指标里剔掉，避免算法被冤枉

### 13.9 功能设想：配置式检测任务

落实：**已实现**（平台层的数据源 → 指标 → 检测任务三段式，`$timefilter` 动态替换）。
