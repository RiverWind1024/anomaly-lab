# LAB · 指标预检实验台

> **一句话**：一个指标在真正建检测任务之前，先取一段真实数据做一次完整预检——
> 看形态、跑多个算法、分析效果、满意了再一键建任务。

## 0. 定位

**是**：

- 指标接入流程的**前置环节**（数据源 → 指标 → **预检** → 检测任务）
- 真实数据上的"上线前评估"：形态是否可识别、算法是否稳定、阈值大概该多少
- 可复现的实验记录：同一份 spec 跑两次结果一致

**不是**：

- 不是合成场景编辑器（合成数据只是 P1 的参考基线，不是主场景）
- 不是通用插件系统（不做动态 import / 沙箱 / 第三方插件）
- 不是工作流引擎（`pipeline` 只留槽，先只实现 `detect` 一步）
- 不是基准报告（实验产物与 `reports/latest` 物理隔离）

## 1. 核心流程

```
选数据（数据源 SQL / 已有指标 / 合成 / 上传）
  → 数据采样（跨时间窗切片，默认 30 天 / 10k 点预算）
  → 数据体检（点数、缺失、零值、间隔、重复时间戳、周期可识别性）
  → 形态推断（6 类 + 置信度 + 理由 + 候选算法）
  → 多算法检测（auto + 候选 + 可选全量）
  → 效果分析（有真值 → F1；无真值 → 检出画像 / 稳定性 / 倍数敏感性）
  → 选型 → 一键建任务（JobDraft 回填）
  → 实验记录（spec + env + result，可复现）
```

## 2. 数据来源与优先级

| 优先级 | 来源 | 说明 | 复用 |
|---|---|---|---|
| **P0** | 已接入数据源 + 临时 SQL | 真实接入流程：数据在库里，指标还没定 | `POST /api/platform/sources/{id}/query`、`series_from_frame`、`$timefilter` |
| **P0** | 已有指标 | 复检老指标、换算法重评 | `load_series(store, metric, ...)` |
| P1 | 合成数据 | 没有真实数据时压测；给真实数据一个"能力参照系" | `generate_series` |
| P2 | CSV / JSON 上传 | 别人给的数据、离线数据 | 新增解析 + 列角色映射 |
| P3 | 公开集（NAB / UCR） | 有真值，验证算法本身 | 已有 loader |

**关键复用**：实验与任务运行必须走同一段清洗路径
（`series_from_frame`：时间解析、排序、group by 拆序列、缺失策略、数据不足判定）。
实验里构造一个**临时 `Metric`（id = -1）**即可，不落库。

> 硬约束：**实验里看到的，就是任务上线后会拿到的**。
> 否则"实验好看、上线打脸"，lab 就是负资产。

## 3. 数据采样策略

### 3.1 为什么需要采样

检测任务每次只看一个窗口（`freq × window_points`）。预检如果只看最近一个窗口：

- 可能正好是业务低谷 / 节假日，结论不可代表
- 无法回答"这个算法在这条指标上稳不稳"
- 无法覆盖月内偶发的异常段

所以预检要在**一段时间范围内取多个与生产同构的窗口**。

### 3.2 窗口定义（生产同构）

| 参数 | 默认 | 约束 |
|---|---|---|
| `window_points` | 500 | 建议与未来任务的 `window_points` 一致；可覆盖 |
| `freq` | 指标的 `freq` | **必须**与指标一致，不可覆盖 |
| `missing_policy` | 指标的策略 | **必须**与指标一致，不可覆盖 |
| `range` | 最近 30 天 | 至少覆盖 `3 × window_points × freq`（周期识别需要 3 个周期） |
| `stride_points` | `window_points`（不重叠） | 可设为 50% 重叠以增加样本 |
| `max_points` | 10_000 | **每条序列**的预算，不是总数 |
| `max_windows` | 100 | 防止窗口太多把 UI / 检测拖垮 |
| `min_valid_ratio` | 0.8 | 有效点不足的窗口丢弃并记录原因 |

窗口数：

```
N = min(
    floor(max_points / window_points),
    floor(span / (stride_points × freq)),
    max_windows
)
```

例：`window_points=500`、`freq=5min`、`max_points=10000`、30 天 →
`min(20, 30天/(500×5min)≈17, 100) = 17` 个窗口。

### 3.3 三种采样模式

| 模式 | 行为 | 适用 |
|---|---|---|
| `recent` | 最近 N 个窗口 | 最接近生产，但只看最近 |
| `even` | 在时间范围内均匀切 N 个窗口 | **默认**，覆盖整段 |
| `stratified` | 先粗扫全段，按数据质量/波动/可疑度分层抽样 | 预检推荐：既要有正常窗口，也要有可疑窗口 |

`stratified` 的粗扫只做廉价统计（每窗的点数、缺失率、零值率、最大稳健 z），
不跑完整检测；用它挑出候选窗口，再对候选做深度检测。

### 3.4 取数实现

**首选：一次拉取整段原始数据 + 本地切窗。**

- 一次查询、结果确定、窗口边界不受分页影响
- 加 `max_rows` 保护（连接器内置 `MAX_ROWS = 100_000`），超过则退化
- SQL 仍然是**指标自己的 SQL**，只是时间范围更宽；聚合粒度由指标定义决定，
  lab 不改写 SQL

**退化：按窗口分页拉取。**

- 整段超过 `max_rows`，或源不支持大结果集时
- 必须按时间顺序拉，记录每个窗口的 `[start, end)`，避免重复/遗漏
- 不做"每个窗口一次查询"作为默认——20 次往返慢且容易被源限流

### 3.5 分组指标的预算

一条 SQL 可能 `group by` 出多条序列（如 50 台主机）。

- `max_points` 是**每条序列**的预算
- 另设 `max_series`（默认 20），超出的序列按"点数最多/缺失最少"排序后截断，
  并如实报告"还有 N 条未纳入"
- 绝不把总预算平均分给所有序列（那会让每条序列都不足）

### 3.6 慢算法保护

`max_windows × detectors` 是检测次数。统计检测器 < 1ms，STL ~31ms，
Chronos ~2s/序列。

- `run all` 默认排除 `SLOW_DETECTORS`
- 慢算法要显式点名，且窗口数上限降到 5
- 结果里记录每个算法的耗时，超预算时提前终止并说明

### 3.7 边界情况

| 情况 | 处理 |
|---|---|
| 数据不足一个窗口 | 明确报"数据不足"，不硬跑 |
| 窗口跨越断流 | 按 `min_valid_ratio` 过滤，记录 `n_missing` |
| 重复时间戳 | 体检报告里标红；窗口内点数异常时丢弃 |
| 采样间隔不规整 | 体检报告里给出实际间隔分布；不静默重采样 |
| 时区 / 夏令时 | 时间解析走指标的 `source_timezone`；窗口起点统一存 UTC |
| 周期不可识别 | 明确提示：当前窗口 `window_points` 不足以识别该周期（如周周期需 ≥ 6048 点 @5min） |

## 4. 评估口径

### 4.1 有真值（合成 / 公开集 / 人工标注）

- 复用 `evaluation/backtest.py` + `metrics.py`
- P / R / F1 / range-F1
- 跨窗口聚合：均值 + 方差（比单窗口可信）
- **阈值校准与测试必须分开**：用前 70% 窗口校准、后 30% 窗口评估；
  在测试窗口上搜阈值属于 oracle 上限，必须显式标注

### 4.2 无真值（真实新数据，主场景）

| 产出 | 说明 |
|---|---|
| 数据质量体检 | 点数、缺失率、零值率、间隔分布、重复时间戳、时间范围、极值 |
| 形态推断 | 6 类之一 + 置信度 + 理由 + 候选算法 |
| 检出画像 | 告警点数/占比、告警区间数、区间长度分布、越界方向分布 |
| 倍数敏感性 | 2.5× / 3.5× / 5× 各报多少点、多少区间 |
| 稳定性 | 跨窗口的形态判定一致性、检出率均值/方差 |
| 耗时 | 每个算法的单窗口耗时 |
| 升级路径 | 复用 `/annotate` 刷选 → 得到真值 → 再算 F1 |

> **原则：无真值时，"检出多"不等于"效果好"。**
> lab 的产出是"证据 + 取舍"，不是"分数"。
> 与项目现有口径一致：缺正例就留空 recall。

### 4.3 可视化

- 单窗口：值 + 基线带 + 分数 + 告警标记（复用 `DetectionChart`）
- 跨窗口：**窗口 × 算法** 矩阵（检出率 / 耗时 / 稳定性），一眼看出哪个组合最稳
- 形态：每窗的判定类别与置信度时间线

## 5. 形态分类与算法覆盖

- `classify(series)` 对任意 `SeriesBundle` 给出 6 类之一，**今天就能用**
- 形态是**推断结果**，不是配置项；真实数据无法指定形态
- lab 要补的是工作流：在**建任务之前**展示推断结果，并允许**覆盖算法**
- 低置信度明确提示"形态可能判错"；记录误判反馈，作为将来分类器改进的素材
- **`MetricClass` 保持 6 类封闭集合**，不为 lab 改成 `str`
- 合成数据的"新形态"是另一件事，单独立项

## 8. 与现有代码的复用与缺口

### 复用

| 已有 | 用途 |
|---|---|
| `Metric` dataclass | 临时 Metric（id = -1），不落库 |
| `series_from_frame` | 时间解析、排序、拆序列、缺失策略 |
| `load_series` | 已有指标直接取数 |
| `classify` / `recommend_for` | 形态推断 + 候选算法 |
| `resolve_detector` / `create_detector` | auto 解析 + 实例化 |
| `compute_bands` / `severity_from_conditions` | 基线带 + 分级 |

| `DetectionChart` / `PreviewPanel` | 前端图表 |
| `/annotate` | 人工标注 → 升级为有真值 |

### 缺口

1. **无 job 的检测路径**：`_compute_job` 强依赖 `job`。需抽出
   `run_detectors(series, detectors, params, rules) -> list[DetectionResult]`，
   让 lab 与 job 共用。
2. **跨窗口采样**：现有 `SourceQueryIn` 只算"最近一个窗口"。
   需新增 `range + stride + mode` 的采样层。
3. **跨窗口聚合**：现有 `BacktestRow` 是单序列一行，需增加窗口维度。

## 9. 分期与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 预检** ✅ | 数据切片 + 采样 + 体检 + 形态推断 | 选数据源/指标 + 范围 → 看到 N 个窗口、质量、形态、置信度、候选算法，不用建任务 |

| **P4 流程插槽** | `transform` / `postprocess` | 有 3 个真实用例再做 |

- 警告涵盖：没有取到数据、范围不足一个窗口、大半窗口为空（附**数据实际覆盖区间**）、

**前端**

- `/lab` 页面（侧栏「数据 → 指标预检」）：选数据源/指标或临时 SQL → 时间范围 →
  采样参数 → 看到窗口质量、形态、置信度、候选算法
- 数据源 / 指标 / 时间范围 / 窗口点数都进 URL —— 结果页可收藏、可分享
- 不跑检测、不写 `reports/latest/`
### 9.2 P1 已落地

**后端**

- `src/anomaly_lab/lab/detect.py`：`run_experiment(store, data_root, spec, detectors, multipliers)`
- `POST /api/lab/run` —— 同一批窗口上跑多个算法，产出对比画像，**不落盘**
- **`inspect` 与 `run` 共用 `prepare()`** —— 两阶段看的是同一批窗口，这是结论可迁移的前提

**无真值口径**（没有 F1，产出「证据 + 取舍」）：

| 指标 | 含义 |
|---|---|
| 检出点 / 检出率 | 异常点占有效点的比例 |
| 有检出的窗口 | 几个窗口报出了东西（太集中说明不稳） |
| 稳定性 | 各窗口检出率的**离散度**（越小越稳） |
| 耗时 | 该算法在全部窗口上的总耗时 |
| 倍数敏感性 | 告警倍数从 1.5 到 4.0 时检出量怎么变 |
| 实际用的算法 | `auto` 逐窗口解析后的算法分布 |

**倍数敏感性零额外算力**：分数只算一次，换一套告警规则表重判等级即可。

**实测结论**（demo 数据，4 个窗口）：

- `zscore` 在 3.5× 时检出归零 —— **对阈值极敏感**，上线后难调；
- `iqr` 稳定（离散度 0.0022）但几乎不报（1/800）—— 稳而无用；
- `stl_residual` 检出 26% 但倍数从 1.5 到 4.0 只从 299 降到 179 —— 阈值调它没用
  （残差比例与 z 分数不同量纲），且慢 100 倍；
- `auto` 逐窗混用两个算法（季节性分组×2 / IQR 围栏×2），**随倍数变化最平缓** ——
  说明混用确实比任一固定算法更鲁棒。

⚠️ 这组数字说明一件事：**光看「检出量」会选错算法**。检出最多的那个恰恰最难调。

**补齐：窗口时序图**（P1 的最后一块）

光看「检出 15 个」这种数字，没法判断这 15 个是尖峰还是噪声边缘 ——
所以逐窗明细的行可以**展开**，展开后是这一窗的时序图：

- `POST /api/lab/window` —— 拉单个窗口的详细数据（值 / 分数 / 基线带 / 告警点）
- **按需拉取**，不塞进 `/api/lab/run` 的响应 —— 一次实验可能上百个窗口，
  全量带曲线会把响应撑爆
- 图上标的告警点数 **必须与对比表里的 `n_alerts` 一致**（同一套单档 P1 规则），
  两处口径不一样的话，用户会对着图和表互相怀疑

图上三个要点：

- **实际值主线** —— 形态（周期 / 趋势 / 尖峰 / 平坦）一眼可见；
- **告警点散点** —— 谁在哪些点报了；
- **基线虚线默认收起** —— 六个算法各画一条基线会把形态彻底淹掉，
  基线是参考不是主体，点图例能展开。

另外 `auto` 常常解析成某个固定算法，两者画出来一模一样 ——
所以图上按**实际算法**去重，只画一条。

```
  id / version / created_at
  spec    —— 参数（含 seed）、指标名、实际生效的 freq、采样配置、算法与倍数
  env     —— git_sha / git_dirty / python / 依赖版本（numpy·pandas·scipy·statsmodels）
  result  —— 与 `/api/lab/run` 同一份返回
  fingerprint —— 剔除耗时后的内容 sha256
```

**可复现怎么保证**

- 指纹**剔除 `elapsed_ms`** —— 耗时每次都变，它不该影响「两次是否一致」的判定。
- 验收方式：同一 spec 跑两次真实检测，比对指纹（`tests/lab/test_records.py`）。
- 记录的是**屏幕上看到的那份结果**，后端不重跑 —— 重跑会因数据源变化与屏幕对不上。

**物理隔离**：实验产物只落 `data/lab/experiments/`，**永不写 `reports/latest/`**
（那是 `make evaluate` 的地盘）。测试里有断言守着这条。

**一键建任务（JobDraft）**

草稿只**回填表单**，不创建任务：

| 字段 | 来源 |
|---|---|
| `metric_id` | 实验的 `spec.metric_id`（临时 SQL 的实验不给建任务） |
| `window_points` | 实验的采样窗口点数 —— 必须一致，否则「实验所见 ≠ 上线所得」 |
| `interval_seconds` | 实验实际生效的 `freq` 换算 |
| `detector` | 优先 `auto`；备选列进 `alternatives`，让人自己挑 |
| `alert_rules` | 实验的主倍数（2.5）+ P0 档（×1.5） |
| `rationale` | 为什么推荐它 —— 检出量、实际用的算法、跨窗离散度 |

**前端**

- `/lab` 页面新增「实验记录」区块：保存这次实验 + 历史记录列表
- 记录行上「一键建任务」→ 跳 `/jobs?experimentId=…`
- `/jobs` 识别该参数 → 拉草稿 → 打开任务表单并回填，顶部说明「这些值是怎么选出来的」
- 关闭表单时清掉 URL 里的 `experimentId` —— 刷新不该又弹一次

### 9.4 P3 已落地：有真值模式

**一句话**：数据自带真值时，lab 除了「检出画像」还能给 **P / R / F1**，
而且**校准与测试分开** —— 校准集选阈值，测试集报成绩。

⚠️ **为什么必须分开**：同一批数据既选阈值又报 F1，F1 一定虚高。
那说明的不是「这个算法有多好」，而是「这个阈值在这批数据上有多贴合」。

**数据来源扩了四种**（`DataSpec.kind`）：

| kind | 取数 | 真值从哪来 |
|---|---|---|
| `metric` | 已有指标 | `truth="annotation"` → 读人工标注；否则无真值 |
| `sql` | 临时 SQL | 同上 |
| `synthetic` | 合成数据 | **自带**（生成器注入的异常区间） |
| `public` | 公开集（NAB / UCR） | **自带**（loader 写的点级标签） |

⚠️ `kind` 决定「怎么取数」，`truth` 决定「真值从哪来」—— 两件事正交，
所以指标也可以挂人工标注。

**后端**

- `src/anomaly_lab/lab/evaluate.py` —— `evaluate_experiment` / `score_windows` /
  `calibrate` / `evaluate_at` / `split_by_series`
- `src/anomaly_lab/lab/truth.py` —— 人工标注的读取与**时间轴对齐**
- `POST /api/lab/evaluate` —— 一次有真值评估

**三个关键口径**

1. **按序列内的时间顺序切窗口**，前一半校准、后一半测试。
   窗口本身不跨界 —— 跨界的窗口会同时用到两半的数据，真值就泄漏了。
2. **逐窗口搜阈值，再取中位数**。每个窗口的分数尺度自成一体，
   把所有分数拼起来搜会被尺度最大的那个窗口带跑。
3. **判定用 `scores >= threshold`** —— 与平台告警同口径，
   lab 的第一原则是「实验里看到的 = 上线后拿到的」。

**验收：合成场景下算法排名与离线评测一致**（`tests/lab/test_evaluate.py`）

- 排名必须一致（用 `evaluation/backtest.py` 那条离线评测做对照）；
- 且 **lab 报出的 F1 一定不高于离线评测** —— lab 用的是「一个阈值管所有窗口」
  （生产语义），离线评测用的是「每条序列各自最优阈值」。
  lab 报得更高就说明阈值用到了测试集的信息（有泄漏）。

**踩到并修掉的两个坑**

| 坑 | 后果 | 修法 |
|---|---|---|
| 均匀采样会**漏掉稀疏的异常点** | 漏掉的异常不进统计，召回率是假的 | 有真值时把含真值的窗口**补进**采样结果（超预算也保留） |
| 人工标注原先存的是**数组下标** | 序列一滚动，同一个下标指向别的时刻，标注整段错位 | 改成存**时间戳**（naive ISO）；`truth.py` 按时间轴对齐 |

⚠️ 公开集（NAB）每条序列只有 1 个异常点 → 校准集与测试集切不开 →
实现会**如实退化**（用平台默认倍数评估）并给出警告，
而不是假装做出了一个校准结果。公开集本就不用于调参。

**前端**

- `/lab` 页面数据来源加「合成数据」（形态 / 点数 / 异常数 / 频率 / 种子）
- 顶部加「有真值评估」按钮 → `TruthEvalPanel`
- 结果表：算法 / 校准阈值 / 校准 F1 / 测试 F1 / 测试区间 F1 / 平台默认阈值 F1 /
  检出点÷真值点；展开行是各阈值下的测试成绩
- ⚠️ `auto` 常常就解析成某个固定算法 —— 算法列写成「自动推荐 → 季节性分组」，
  否则两行一模一样的数字会让人以为跑出了两个结果

### 9.5 生产检测记录也纳入统计

**问题**：评估报告里那 480 行**全是基准数据**（120 序列 × 4 算法）。
生产任务跑出来的东西、用户标过的异常，一条都没进统计。

**两个「场」的分工**：

| | 基准场 | 生产场 |
|---|---|---|
| 数据 | 合成集 / 公开集 | 平台的**检测记录**（`cache/platform/runs/<run_id>/`） |
| 真值 | 自动注入 / loader 自带 | **人工标注** |
| 回答 | 算法本身有多好？换算法值不值？ | 这个指标上线后效果如何？阈值要不要调？ |
| 覆盖 | 全集 | **只有被标注过的那部分** |

⚠️ **预测侧直接用线上跑出来的那份**，不重跑 ——
重跑算的是「现在跑会怎样」，不是「当时跑成了怎样」。
run 的 npz 里已有 `timestamps / values / scores / severity`，时间轴与波形都齐，
**不需要改 runner**。

⚠️ **标注按「序列 + 时间区间」存，不按运行**（`annotations/<series_id>.jsonl`）——
真值是**数据的属性**，不是某次运行的属性。滚动窗口下同一个异常会被
连续几十次运行反复报出，按 run 存等于让用户把同一段标几十次。
**一次标注，所有时间轴覆盖该时段的检测记录都复用**（实测：1 条标注被 12 条记录复用）。

⚠️ `run_series` 表存了每次检测的**时间范围**（`start_ts` / `end_ts`）——
「这条标注落在哪几次检测里」是一条 SQL，逐条读 npz 太慢。

**「核对过」是独立的标注类型**（`type="reviewed"`）——

| 类型 | 内容 | 作用 |
|---|---|---|
| 异常区间 | `type=spike/drift/…` + `start`/`end` | 真值 |
| `reviewed` | 只有 `run_id`，**没有边界** | 覆盖率声明 + **负样本标签** |

⚠️ **没有负样本标签，就没有分母**：
一条 6 分钟的标注会让同一窗口里其余几十个告警点凭空变成误报。
所以评估**只在 `reviewed` 覆盖的时间段里计分**；
老标注没有 `reviewed` 记录 → 退化成「只在标注区间内计分」（保守，不凭空产生误报）。

⚠️ 报告会给出**核对覆盖率** —— 只核对了一小段时直接说出来，
「25 个告警里 2 个真」和「25 个告警里 2 个被核对过」是两回事。

### 9.5.1 检测记录落库

⚠️ **「检测记录」以前只躺在文件系统里** —— `index.json` 有序列摘要、
npz 有逐点数组，但**数据库里一个字都没有**。后果有三个：

| 后果 | 实测 |
|---|---|
| 查询要扫文件系统 | 8700 多个产物目录 = 0.47s，且随运行数线性涨 |
| 告警历史会消失 | 保留策略 prune 掉目录，告警就没了 |
| 双重事实来源 | `runs` 表说「run 1000 有 25 个告警」，明细只在 npz 里 |

**分两层落库**（`platform/store.py`）：

| 表 | 内容 | 为什么进库 |
|---|---|---|
| `run_series` | 每次运行 × 每条序列的摘要（`n_alerts` / `detector` / `metric_class` / `content_hash`） | 要按维度聚合、要做抽样 —— 扫目录做不了 |
| `alert_events` | 每次运行报出的**告警区间**（`level` / `start_ts` / `end_ts` / `n_points` / `max_score`） | 这才是「检测记录」的业务含义；且要留存、要查 |

⚠️ **逐点数组（timestamps / values / scores / severity）仍留在 npz** ——
那是图表回放与评估反算的原材料，350MB 塞进 SQLite 没有好处。

⚠️ **老库要补录** —— `anomaly-lab sync-detections` 把磁盘上的产物灌进库（幂等）。

### 9.5.2 分层维度：数据源 → 指标 → 检出结果

⚠️ **总体 = 所有检测记录，检出正常和异常的都算**：

| 层 | 说明 | 决定什么 |
|---|---|---|
| **异常**层 | 报出了告警的记录 | **Precision** —— 告警里有多少是真的 |
| **正常**层 | 什么都没报的记录 | **Recall** —— 真异常里有多少被漏掉 |

⚠️ **正常层是估漏报的唯一来源** —— 只标异常记录的话，
**漏报永远是 0**，Recall 会被严重高估（分母里根本没有真异常）。

⚠️ **两层的采样率必须不一样** —— 正常记录远多于异常记录
（实测 108 条里 84 条什么都没报），同一个采样率要么正常层标不完、
要么异常层样本太少。默认**异常层 50% / 正常层 5%**。

| 层内 | 说明 |
|---|---|
| 候选 | 该层全部检测记录（**每一次运行** × 每条序列） |
| 采样 | 层内等间隔抽 `rate` 比例，且**每层封顶** `max_per_layer` 条 |
| 已标注 | 采样出来、被人工标过真值的那些 |

⚠️ **等间隔而不是随机**：随机抽样每次结果都可能不同 →
用户标过的记录下次就不在样本里了，标注全白费。
等间隔（按 run_id 排序 = 时间顺序）既确定又能覆盖时间跨度。

⚠️ **每层封顶**：采样率是相对比例，总体一大就还是标不完
（实测 3 万条候选 → 20% 仍是 6000 条）。标注是人工的，每层十几条才现实。

⚠️ **抽样单位就是「一条检测记录」，不去重** ——
活数据源每次检测的内容都不同（实测 12657 条记录 = 12657 种内容）。
只有静态数据源 / 手动重跑才会重复，那时 `n_contents` 会把差异显示出来。

### 9.5.3 反算：不是「只算样本」，也不是「各样本 F1 取平均」

一条记录在 20% 采样率下被抽中，它就**代表总体里的 5 条**。
所以总体混淆矩阵是 **Σ (1/rate) · 单条计数**，P / R / F1 再从这个矩阵算。

⚠️ **比率不能平均** —— 「各样本 F1 的平均」会把小样本的极端值放大，
和「先加总计数再算比率」不是一回事。

⚠️ **采样率会变，所以它必须跟着标注一起存**：
标注记录上带 `rate`（标它时所在层的采样率）。
采样率后来从 20% 改成 50%，**老标注仍按 5 倍算** ——
它是从那个样本框里抽出来的，代表的框没变。
（老标注没记 rate 的，退化成权重 1 —— 保守但诚实。）

⚠️ **反算用的是「所有已标注的记录」，不限于当前采样选中的** ——
标注是稀缺资源，标过的都要用上；权重由各自的 rate 决定。

⚠️ **区间级 F1 不能像 TP/FP/FN 那样反算**（区间不是可加的计数），
界面给的是按权重的加权平均 —— 供参考，不是总体估计。

⚠️ 报告必须同时给**候选数 / 采样数 / 已标注数** ——
只给一个漂亮的 F1 是在骗人。界面上直接写明
「只覆盖被标注过的那部分，不代表整体效果」。

⚠️ **检测记录数 ≠ 告警事件数** —— 重复倍数是 `检测窗口 / 运行间隔` 算出来的
**配置结果**（窗口 10 分钟、间隔 2 分钟 → 5 倍；窗口 5 小时、间隔 1 分钟 → 300 倍）。
短窗口下历史异常很快滑出，不会重复；剩下的那点重叠是**告警系统的去重/抑制**该管的，
评估侧不做。`n_events` 按 `(level, start_ts, end_ts)` 去重后统计，
作用只是**让你看得见这个倍率**。

**后端**

- `src/anomaly_lab/evaluation/production.py` —— `list_samples` / `evaluate_production`
- `src/anomaly_lab/platform/backfill.py` —— 把产物补录进库

  （参数 `rate_alert` 异常层采样率、`rate_normal` 正常层采样率、

⚠️ **候选清单查数据库，不扫文件系统** —— 「有哪些检测记录」是一条 SQL。
