# spec 2：假远端时序数据库 + 活数据

> 状态：已定稿（2026-11-02）
> 前置：spec 1（数据源连接器 + 数据浏览器）已合入 master
> 后续：spec 3（检测记录筛选分页）、spec 4（数据保留与清理）

## 1. 目标与动机

spec 1 把「SQL 透传」的**通路**做完了：平台能把 SQL 原样发给远端、拿回结果集。
但通路两端还缺一头 —— **没有一个真的远端**。

现在演示 HTTP 透传只能靠一个一次性的假网关（不入库），它有三个问题：

- 数据是死的，跑一次就完；
- 形态是我们自己编的，不是一个「像样」的时序库；
- 换 url 不能直接接真 InfluxDB（接口形状对不上）。

spec 2 补这一头：做一个**照 InfluxDB 3 API 形状**的假远端，持续产数。
它的价值不只是演示，还包括：

| 价值 | 说明 |
|---|---|
| **验证 D11** | 浏览预览与指标运行时必然一致 —— 现在有了一个「远端自己执行 SQL」的端点可以对照 |
| **验证连接器一致性** | spec 1 测试策略要求「sqlite 与 http 跑同一套用例 → 两条路径返回相同 SeriesBundle」。假远端就是那个共同后端 |
| **端到端演示** | 数据源 → 指标 → 检测 → 告警 全链路有一条「活的」数据在流动 |
| **可换真库** | 接口形状照抄 InfluxDB 3 → 换 url + token 就能接真的 |

## 2. 范围

### 做

- 一个独立的 HTTP 服务，实现 InfluxDB 3 的 `POST /api/v3/query_sql`
- 后台线程持续写入数据（周期型流量、抖动 CPU、尖峰 / 漂移 / 断流）
- 数据落 SQLite（**自己开 WAL**），远端自己执行 SQL
- 一条命令把平台侧的 HTTP 数据源 + 指标 + 检测任务**配好**（不用手点）
- 文档 + 测试

### 不做

- InfluxQL 端点（`/api/v3/query_influxql`）—— spec 1 已定第二层连接器只预留位置
- 写入端点（`/api/v3/write_lp`）—— 假远端自己造数，不接受外部写入
- parquet 响应格式 —— 需要 pyarrow，本项目零新依赖
- 鉴权（token 校验）—— 见 D61

## 3. 关键设计决策

### D60：假远端是**独立进程**，不是平台的一个模块

假远端跑在自己的进程里（`python -m anomaly_lab.mock_tsdb`），监听 8181。

**为什么不是平台内的一个路由**：平台进程内的话，平台和「远端」共享内存与生命周期，
测出来的「远端调用」不真实（比如连接池、序列化、超时都不成立）。
独立进程才能真正验证 `urllib` 那条路 —— 连接失败、超时、502 都是真的。

**为什么不是 `scripts/` 下的一个文件**：它要被测试直接 import（要能起一个
`TestClient` 级别的实例），也要能作为库被平台侧引用（比如「配好一条演示数据源」
的逻辑要用它的常量）。放 `src/anomaly_lab/mock_tsdb/`。

### D61：不实现鉴权

InfluxDB 3 的 `query_sql` 需要 `Authorization: Bearer <token>`。
假远端**不校验** token，但**接受并忽略**这个头。

**为什么**：鉴权会让「换 url + token 接真库」这件事在演示里多一道坎，
而这个假远端的价值在于「数据在流动」，不在于「权限模型」。
真库怎么鉴权是连接器 `config.headers` 的事，spec 1 已经做完了。

⚠️ 文档里必须写明：**这是假远端的简化，不是平台的简化**。平台侧照样支持
在 `config.headers` 里带 `Authorization`。

### D62：数据落 SQLite，**自己开 WAL**

假远端的数据存一个 SQLite 文件。假远端**自己** `PRAGMA journal_mode=WAL`。

**为什么开 WAL**（spec 1 §11 约束 1 的延续）：平台以 `mode=ro` 打开它，
只读连接与写入连接并发时，WAL 允许「写者不阻塞读者」。

⚠️ **实测结论（spec 2 专门验证过）**：
- 写者活跃时，跨进程 `mode=ro` 能读到**已提交**的最新数据；
- 写者被 `kill -9`、`-wal` 残留且 `-shm` 丢失时，`mode=ro` **仍能打开并读到数据**；
- 读到的行数与写者提交的一致 —— 没有丢数据，也没有读到脏数据。

这是 spec 1 留下的未验证假设，现在有实测结论了。

### D63：假远端执行的是**真 SQL**，不是查表

`query_sql` 收到的 SQL **原样**在 SQLite 上执行（`SELECT` 只读）。

**为什么不用「假装执行」**（比如解析出表名再拼 SQL）：
平台的浏览端点会让用户写**任意**只读 SQL，`$timefilter` 也是拼进去的。
假执行器解析不了通用 SQL。真 SQLite 反而最省事 —— 它本来就是完整 SQL 引擎。

⚠️ **只读**：执行前用平台同款的只读校验拦一道（`validate_readonly_sql`），
避免假远端变成一个「能删库的 HTTP 端点」。

### D64：数据形态 —— 4 条曲线，覆盖平台的检测能力

假远端造 4 条序列，各自形态不同，让平台的检测器有东西可测：

| 序列 | 形态 | 演示什么 |
|---|---|---|
| `web-traffic` | 周期型（每天一个波峰） | 正常基线，不该报警 |
| `api-latency` | 平稳 + 抖动 | 噪声大但不异常，不该报警 |
| `db-pool` | 周期型 + 尖峰 | 该报尖峰型异常 |
| `cache-hit` | 周期型 + 漂移 | 该报漂移型异常 |

**为什么要专门造这几条**：平台的检测器有「数据不足」「基线算不出来」等分支，
没有合适形态的数据，那些分支永远测不到。平稳型能验证「不该报警时不报」。

**断流**：另有一段「数据停止」的时间窗（某个 `series` 在某段时间没点）。
这是 `missing_policy` 的用武之地 —— 验证缺失值策略真的生效。

### D65：断流用「不写点」实现，不用 NULL

断流 = 那段时间**根本没有行**（不是写了 NULL 值）。

**为什么**：`missing_policy` 处理的是「值列里的缺失」。
不写行的话，那段时间在序列里就是**缺一段**，`drop` 策略下点数变少，
`interpolate` 策略下…… ⚠️ 这里有个真实的边界：pandas 不会自动补点，
`interpolate` 只在**有行的 NaN 值**之间插值。

**结论**：断流（不写行）与「值缺失」（写 NULL）是两件事。
假远端造**两种**：
- 断流：整段时间不写行 → 序列点数变少（验证 `drop` 之后点数对）
- 值缺失：写了行但值是 NULL → `missing_policy` 真正生效的路径

⚠️ SQLite 的 CSV 输出：NULL 会变成空字符串。平台的 `_parse_csv` 用
`pd.read_csv` → 空值变 NaN ✓ 正好。

### D66：响应格式 —— CSV 优先，JSON/JSONL 兼容

InfluxDB 3 的 `format` 取值：`json`（默认）/ `csv` / `jsonl` / `pretty` / `parquet`。

假远端实现 `csv` / `json` / `jsonl` 三种（`pretty` 与 `parquet` 返回 400，
明确说明不支持）。

⚠️ **JSON 格式用「对象数组」而不是 InfluxDB 3 的两段式**（`results[].series[]`）。
理由：spec 1 已明确「平台不支持两段式响应，接 InfluxDB 3 请用 `format=csv`」。
假远端既然是「照抄 API 形状」，那**`csv` 必须是主通路**（这是真 InfluxDB 3
推荐的接法），JSON 用对象数组则让平台也能用 `format=json` 连它。

**这不是「抄错」而是「抄对了接法」**：真 InfluxDB 3 用 csv，假远端也用 csv，
两边接法一致。JSON 的两段式差异记在文档里。

### D67：`db` 参数照抄，但只认一个库

InfluxDB 3 的 `query_sql` 要求 `db` 字段。假远端**要求**这个字段存在
（缺失 → 400），值可以是任意字符串（只有一个库，不校验库名）。
照抄的是「有这个参数」这个形状。

### D68：时间列用 `+00:00` 格式存

假远端存的时间是 `2026-11-02T10:00:00+00:00`（T 分隔 + `+00:00`）。

**为什么不用 `Z`**：平台的 HTTP 方言生成的时间字面量是 `+00:00` 格式
（spec 1 D55 的决定）。假远端用 SQLite 执行，**SQLite 对 TEXT 列做字典序比较**。
`Z` 结尾与 `+00:00` 结尾的字符串**字典序不匹配时间序** → 边界行会被误判。

⚠️ 实测：存储用 `Z` 时，`>= '...+00:00'` 的边界判断与真 InfluxDB 3 的
timestamp 语义不一致。存 `+00:00` 才与平台的 SQLite 侧方言一致。

**推论**：接真 InfluxDB 3 时，平台的 `iso_utc` 字面量 `+00:00` 发过去，
真库按 timestamp 类型比较 —— 语义正确 ✓。所以这个格式对真库也对。

### D69：平台侧提供「一键配好」的路径

光有假远端不够 —— 用户还得手动在 UI 里填 url、body、写指标 SQL。
那是 5 分钟的手工活，不适合「给别人看」。

做法：假远端启动时（或一个独立的 seed 命令）把平台侧的
**HTTP 数据源 + 指标 + 检测任务**建好，幂等（重复跑不重复建）。

**为什么不在平台进程内做**：数据源配置属于平台的数据，配置动作属于平台。
放在 `platform/` 下做成一个 `seed_mock_remote(data_root)` 函数，
由 CLI 命令调用。这样「假远端」与「平台侧配置」职责分明：
假远端只管造数与查询，平台侧配置是平台的事。

## 5. 造数设计

### 5.1 曲线形态

每条曲线是「基线 + 噪声 + 异常注入」，全部**确定性**（seed 固定 → 每次一样）。

| 序列 | 基线 | 噪声 | 异常注入 |
|---|---|---|---|
| `web-traffic` | 日周期正弦（周期 1 天，振幅 30） | 高斯 σ=3 | 无 |
| `api-latency` | 常数 50 | 高斯 σ=8 | 无 |
| `db-pool` | 日周期正弦（周期 1 天，振幅 10） | 高斯 σ=1 | 每 ~30 点一个尖峰，幅度 ×3，持续 2 点 |
| `cache-hit` | 日周期正弦（周期 1 天，振幅 5） | 高斯 σ=0.5 | 后 60% 时间窗内基线线性上移（漂移） |

⚠️ **噪声要「连续」而不是「逐点独立」**：逐点独立的高斯噪声看起来是白噪声，
不是「抖动的 CPU」。做法是把噪声按时间索引的**固定哈希**取 ——
`numpy.random.default_rng([seed, point_index])` —— 保证同一索引恒等，
且相邻点噪声也不相关……

⚠️ 那怎么造「相关噪声」？用 **AR(1)**：每点依赖前一点。
但增量写入时前一点的值要能取到 → 造数器要**按顺序**算。

**决策**：造数器按时间顺序增量计算（维护上一个点的状态），
用 `np.random.default_rng([seed, index])` 取每点的**创新项**（innovation），
AR(1) 递推。这样：
- 确定性：同一 index 的 innovation 恒等 ✓
- 相关性：AR(1) 递推给出连续抖动 ✓
- 增量：只需记住上一个值 ✓

### 5.2 时间栅格

采样间隔 **1 分钟**。写入时刻对齐到分钟边界（`now` 向下取整到分钟）。
这样 `$timefilter` 的字面量（秒级）永远落在栅格上，不会出现「半分钟点」。

⚠️ 平台的 `freq` 字段是 `5min` 之类的字符串，而假远端是 1 分钟采样。
指标的 `freq` 描述的是**采样频率**，1 分钟 → `1min`。平台 `freq_delta` 支持
`1min` ✓（`_FREQ` 正则 `^(\d+)(s|min|m|h|d)$`）。

### 5.3 落库

表结构：

```sql
CREATE TABLE IF NOT EXISTS metrics (
    ts   TEXT NOT NULL,   -- 2026-11-02T10:00:00+00:00
    series TEXT NOT NULL,
    value REAL
);
CREATE INDEX IF NOT EXISTS idx_metrics_ts ON metrics(ts);
```

⚠️ **时间列存 TEXT 而不是 INTEGER**：SQLite 的字典序比较要求格式统一，
TEXT 存 `+00:00` 格式时字典序 == 时间序（同一偏移、同一格式下）。
INTEGER epoch 则要平台侧改方言 —— 不做。

### 5.4 断流与值缺失

- **断流**：`db-pool` 在启动后的第 3 小时起，有一段 20 分钟没有点。
- **值缺失**：`api-latency` 偶尔写 NULL 值（每 ~50 点一个）。

⚠️ 这两者在 SQLite 里都成立：断流 = 那段时间**没有行**；
值缺失 = 有行但 `value IS NULL`。

## 6. 平台侧配置

`platform/mock_remote.py` 提供 `seed_mock_remote(data_root, base_url, db)`：

| 对象 | 配置 |
|---|---|
| 数据源 | `kind=http`，`name="mock-tsdb"`，`config.url = {base_url}/api/v3/query_sql`，`method=POST`，`body = {"db": ..., "q": "{sql}", "format": "csv"}`，`format=csv` |
| 指标 | `query = "SELECT ts, series, value FROM metrics WHERE $timefilter ORDER BY ts"`，`time_column=ts`，`value_column=value`，`group_column=series`，`time_format=iso_utc`，`freq=1min` |
| 检测任务 | `detector=iqr`，`window_points=60`，`interval_seconds=60` |

⚠️ **`{sql}` 在 body 里**（不是 url）—— body 里的替换是原样的，SQL 不会被
百分号编码污染（spec 1 的决定）。url 里没有 `{sql}`。

⚠️ **`format=csv` 且 body 里也写 `format=csv`** —— 两者必须一致，
否则平台报 400（spec 1 的「请求的格式与解析的格式必须对齐」）。

⚠️ **指标 SQL 的表名/列名必须与假远端的表结构一致**：
`metrics(ts, series, value)`。

⚠️ **`group_column=series`** → 4 条序列 → 检测任务产出 4 条序列。

## 7. 端点契约

假远端的端点**不在平台的契约守卫范围内**（那是给平台自己的端点用的）。
但平台的端点契约（`EXPECTED_PATHS` / `test_api_contract.py`）**不变** ——
spec 2 不给平台加新端点。

⚠️ 唯一可能变的是：平台的 CLI 加一个命令（不是 HTTP 端点）→ 不影响契约。

## 10. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 假远端的 SQL 引擎（SQLite）与真 InfluxDB 3（Arrow）方言不同 | 文档明说：假远端验证的是**平台的通路**，不是远端方言；接真库时若 SQL 不兼容是远端的事 |
| 后台线程一直写 → 库无限增长 | 假远端**只保留最近 N 小时**的数据（滚动删除）。⚠️ 这也满足 spec 4 的「不能清掉模拟源的当前窗口」—— 详见下 |
| 演示时数据断流 → 看着像坏了 | 断流只在**指定序列**的**指定窗口**发生，且窗口很短；其余序列持续 |
| 端口 8181 被占 | 端口可配（`--port`）；启动时明确报端口占用 |
| 平台的 `data/platform/source.db` 被污染 | 假远端的数据**单独放** `data/mock_tsdb/` |

### 与 spec 4（保留与清理）的衔接

spec 4 要做平台的保留策略（runs 表、npz 目录、feedback、annotations）。
假远端的数据**不在 spec 4 的范围内** —— 它是另一个进程的数据，
平台管不到。

**但约束仍在**：spec 4 的清理不能清掉模拟源的当前窗口。
因为假远端的数据在独立目录 `data/mock_tsdb/`，平台侧的清理不会碰它 ✓。
假远端自己的滚动窗口（保留最近 N 小时）保证它不会无限增长。

⚠️ 这条衔接要写进 spec 4 的设计文档 —— **spec 4 只管平台侧**。

## 11. 验收标准

1. `make mock-tsdb` 起假远端，`curl` 它的 `query_sql` 拿到 CSV；
2. `make mock-demo` 在平台侧建好源/指标/任务；
3. `make serve` 后，能在 UI 里看到这条 HTTP 源、浏览它的数据、
   指标跑出 4 条序列、尖峰那条报出告警；
4. 数据**在流动** —— 等两分钟再查，新点出现了；
5. 连接器一致性测试通过（sqlite 与 http 两条路径结果相同）；
6. WAL + 只读测试通过；
7. 后端测试全绿、`make lint` 全绿、前端不受影响（本 spec 不改前端）。
