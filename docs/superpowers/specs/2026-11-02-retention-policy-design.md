# spec 4：数据保留与清理策略

> 状态：已定稿（2026-11-02）
> 前置：spec 1（连接器）、spec 2（假远端）、spec 3（检测记录筛选分页）已合入 master
> 后续：容器化（贯穿性工作，最后做）

## 1. 目标与动机

平台的任务**每 5 分钟就产生一次运行记录**。实测（本机跑了两天）：

| 产物 | 位置 | 当前量 |
|---|---|---|
| 运行记录行 | `platform.db` 的 `runs` 表 | **803 行**（2 个任务 × 2 天） |
| 检测结果文件 | `data/cache/platform/runs/<run_id>/*.npz` | **14 MB**（803 个目录，每个 2 个 npz） |

**没有任何东西会清理它们**。按这个速度，一年就是 21 万行、约 4 GB。

这不是「以后再说」的问题 —— 平台已经跑了两天，垃圾就在那儿，而且**作品集演示时**，
别人翻到 800 条一模一样的运行记录，第一反应是「这玩具撑不住真实数据量」。

需求原话是「所有不断产生的数据要自动清理」。这句话要落到具体范围上：

- **自动** —— 不需要用户手动点某个按钮；
- **不断产生** —— 排除「用户手工造的数据」（标注、反馈），
  它们不是「不断产生」的，是一次性的；
- **数据** —— 数据库里的行 + 磁盘上的文件，两个都要。

## 2. 范围

### 做（平台侧）

- `runs` 表按保留窗口清理
- `data/cache/platform/runs/<run_id>/` 目录按保留窗口清理
- **孤儿目录**清理（DB 里没有对应记录、但目录还在）
- 清理**触发器**：调度器自动（节流）+ CLI 手动命令
- 保留策略**参数化**（环境变量 + CLI 覆盖）
- 存储占用**可见**：`/api/platform/storage` + 概览页展示
- 手动触发：`POST /api/platform/prune`

### 不做（明确排除）

| 不做什么 | 为什么 |
|---|---|
| **人工反馈**（`feedback` 表） | 人工产生的数据，一次性的，不是「不断产生」。删它是破坏用户劳动成果 |
| **标注**（`data/annotations/*.jsonl`） | 回测侧的人工标注，同上 |
| **假远端数据**（`data/mock_tsdb/`） | 不归平台管 —— 它自己滚动保留最近 6 小时（D73） |
| **回测侧检测结果**（`data/cache/detections/`） | `make detect` 的一次性产物，不是调度产生的 |
| **数据集**（`data/synthetic/`） | 同上 |
| 保留策略的**管理界面** | 参数走环境变量 + CLI，够用。可视化设置是另一件事 |
| 按**磁盘配额**清理 | 保留窗口已经给出了上界，再加配额就是两套语义 |

⚠️ **「不归平台管」要在文档里写死** —— 否则后人会以为平台的清理会顺手把假远端的数据也清了，
或者反过来，用平台的清理去管不该管的东西。

## 3. 关键事实（已核实）

| 事实 | 影响 |
|---|---|
| `collect_alert_events` 只读**每个任务的最新一次 run** | 最新 run **绝不能删**，否则整个告警中心变空 |
| `runs` 表的行与 `runs/<run_id>/` 目录**一一对应** | 两者要一起清，否则留下孤儿目录 |
| `feedback.run_id` **没有外键约束**（`INTEGER`，无 `REFERENCES`） | 删 run 时得**手动**把 `feedback.run_id` 置 NULL |
| `runner._INFLIGHT` 登记「正在执行的 job_id → run_id」 | 正在跑的 run 不能删（删了目录，runner 写文件会失败） |
| `list_runs(job_id, limit=20)` 默认只返回 20 条 | 清理需要「全部」—— 要新增取全量的方法 |
| `run_stats()` 统计的是**全表** | 清理后「累计运行」不再是累计值 → 文案要改（D93） |
| `timeutil.to_iso` 输出 `+00:00` 偏移的 ISO 串 | 时间比较用 `parse_iso` 统一解析 |
| 假远端在 `data/mock_tsdb/` | 平台清理的路径碰不到它 |

## 4. 关键设计决策

### D83：保留窗口 = 「每 job 最近 N 次」**∩**「最近 T 小时」

```
保留 = 该 job 的运行中，同时满足「属于最近 N 次」且「started_at 在最近 T 小时内」的
```

- **N**（默认 100）控制**磁盘上界**：不管任务是 5 分钟一次还是 10 秒一次，保留量都封顶。
- **T**（默认 24 小时）控制**时间上界**：每天跑一次的任务不会攒够 100 次就停下。

⚠️ 是 **∩（两个都要满足）** 不是 ∪：

- ∪ = 「最近 100 次 **或** 24 小时内」→ 24 小时内的低频任务可能一次都不删，
  而高频任务会留下远超 100 条。**上界不成立。**
- ∩ = 上界严格成立：保留量 ≤ min(N, T 内的运行数)。

实现上按 `id` 倒序遍历该 job 的运行（`id` 单调，比 `started_at` 可靠），
**遇到第一个不合格的就把它和它之后的都列为待删** —— 时间与序号都单调递减，
后面的只会更不合格。

### D84：每个 job 至少保留**最新一次**运行

即使它超了 24 小时窗口。

理由：告警中心只读最新 run（`collect_alert_events` → `latest_runs()`）。
删掉最新 run 意味着「这个任务现在没有任何告警状态」——
不是「清理掉了旧数据」，是**功能坏了**。

代价几乎为零（多留一份），但守住的是整个告警页。

### D85：不删**正在执行**的 run

`runner._INFLIGHT` 登记着「正在跑的 job_id → run_id」。手动触发与调度到点都登记在里面。

正在跑的 run 被删 → runner 往已删目录写 npz → 抛异常 → 那次运行失败。
**清理由别人触发、却把别人的运行搞坏** —— 不能接受。

### D86：人工反馈**不删**，但要**断开引用**

`feedback` 是人工产生的数据（对某次运行的告警说「这是误报」）。
自动删它 = 自动丢弃用户的劳动成果。

但它有 `run_id` 指向某次运行。运行被删后这个引用会悬空 →
**把 `feedback.run_id` 置 NULL**，保留反馈本身。

⚠️ 表里没有外键约束（`run_id INTEGER`，无 `REFERENCES`），
所以必须**手动 UPDATE**，不能指望 `ON DELETE SET NULL`。

### D87：孤儿目录要清

`data/cache/platform/runs/` 下的目录，如果 `runs` 表里已经没有对应的行，
那是残留（手动删库、异常退出、手工删表都会留下）。

它是**纯垃圾**，没有保留价值 —— 直接清。
判定：以目录名（转 int）查 DB，不在 `runs.id` 集合里即为孤儿。

⚠️ 非数字目录名**跳过**（保守 —— 可能是人放进去的东西）。

### D88：先删**文件**，再删**数据库行**

两者之间崩溃会留下不一致状态，两个方向都有自愈路径：

| 顺序 | 中途崩溃的后果 | 自愈 |
|---|---|---|
| 先文件后 DB | DB 里留了一条指向已删文件的记录 | 下次清理时它仍超窗口，仍会被删 |
| 先 DB 后文件 | 目录成了孤儿，磁盘空间**没释放** | 孤儿清理会捡回来（D87） |

选**先文件后 DB**：磁盘占用的释放是本 spec 的主要目标，
而「DB 里有条记录但文件没了」只是暂时的展示层不一致。

### D89：触发 = 调度器 tick 末尾**节流**清理 + CLI 手动

- **自动**：调度器每次 tick 后检查，**每小时最多清一次**。
  tick 默认每 2 秒一次 —— 每次都全表扫描 + 遍历 800 个目录太浪费。
- **手动**：`anomaly_lab prune`（可 `--dry-run` 先看会删什么）。

放在 `tick()` 末尾而不是独立线程：清理失败要能看到（记日志），
且 `tick()` 本身就是测试入口（调度器测试直接调 `tick()`）。

### D90：参数来源 = 环境变量 + CLI 覆盖

| 参数 | 环境变量 | 默认 |
|---|---|---|
| 保留时长（小时） | `ANOMALY_LAB_RETENTION_HOURS` | 24 |
| 每任务保留次数 | `ANOMALY_LAB_RETENTION_MAX_RUNS` | 100 |

⚠️ **不放数据库**。保留策略是部署参数，不是业务配置 ——
放 DB 意味着要加设置界面、加校验、加审计，超出范围。
环境变量 + CLI 覆盖已经覆盖了「开发时调短、演示时调长、部署时固定」。

### D91：让清理**可见** —— `/api/platform/storage` + 概览页展示

「自动清理」如果完全不可见，用户无法判断它在不在工作。
作品集演示时，「数据在自动滚动」本身就是个卖点。

- `GET /api/platform/storage` —— 当前占用、保留策略、上次清理时间
- `POST /api/platform/prune` —— 立即清理，返回清理统计

⚠️ 新增端点要同步**两处**契约守卫
（`frontend/src/api/endpoints.test.ts` 的 `EXPECTED_PATHS` +
`tests/web/test_api_contract.py`）。

### D92：概览页「累计运行」改成「**保留期运行**」

`runs.total` 来自 `run_stats()`（全表计数）。清理后它不再是「累计」，
而是「保留窗口内的运行次数」。

不改文案就是**界面在撒谎** —— 和 spec 3 修的「重置后日期输入框残留旧值」是同一类错误。

### D93：清理状态存在 `platform.db` 的 `retention_state` 表

「上次清理时间」要跨进程可见（API 请求看到的和调度器写的是同一个状态）。
放平台自己的 DB 里，与其它状态一致。

单行表（`id = 1`），存「上次清理时间 + 上次删了多少」。

## 5. 架构

```
                        调度器 tick（每 2 秒）
                              │
                    ┌─────────┴──────────┐
                    │  节流：每小时一次？  │
                    └─────────┬──────────┘
                              │ 是
                    ┌─────────▼──────────┐
                    │   prune(store,      │
                    │         data_root)  │
                    │  ┌───────────────┐  │
                    │  │ 选待删 run    │  │  select_prunable_runs（纯函数）
                    │  │ 删目录        │  │  D83/D84/D85
                    │  │ 删 DB 行      │  │  D88（先文件后 DB）
                    │  │ feedback 置 NULL│ │  D86
                    │  │ 清孤儿目录     │  │  D87
                    │  └───────────────┘  │
                    └─────────┬──────────┘
                              │
                    写 retention_state（上次时间 / 删了多少）
                              │
                    ┌─────────▼──────────┐
                    │ GET /api/platform/storage → 概览页卡片
                    │ POST /api/platform/prune → 手动触发
                    └────────────────────┘
```

**数据流**（选择逻辑单独抽成纯函数）：

```
runs 表（按 job 分组，id 倒序）
      │
      ▼
select_prunable_runs(runs_desc, policy, now)  ──►  待删的 run_id 列表
      │
      ▼
prune(store, data_root, policy)  ──►  PruneResult
```

## 6. 数据契约

### `GET /api/platform/storage`

```json
{
  "policy": { "max_age_hours": 24, "max_runs_per_job": 100 },
  "runs": {
    "kept": 100,
    "n_dirs": 100,
    "bytes": 10485760
  },
  "database": { "path": "data/platform.db", "bytes": 65536 },
  "feedback": { "total": 3 },
  "last_pruned_at": "2026-11-02T12:00:00+00:00",
  "last_pruned": { "deleted_runs": 703, "freed_bytes": 9989731 }
}
```

### `POST /api/platform/prune`

```json
{
  "deleted_runs": 703,
  "deleted_dirs": 703,
  "orphan_dirs": 0,
  "freed_bytes": 9989731,
  "kept_runs": 100
}
```

`--dry-run` 只报告不删除。

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 误删最新 run → 告警中心变空 | D84：每个 job 至少留最新一次 |
| 误删正在跑的 run → 那次运行失败 | D85：跳过 `_INFLIGHT` 里的 |
| 删掉人工反馈 → 丢用户劳动 | D86：feedback 只断开引用，不删 |
| 平台清理误伤假远端数据 | D87：路径完全不相交，文档写死 |
| 清理跑太频繁 → 拖慢调度 | D89：节流到每小时一次 |
| 「累计运行」文案失真 | D92：改成「保留期运行」 |
| 时间窗口算错 → 删太多/太少 | 纯函数单测覆盖边界（等于 cutoff 的算保留） |

## 10. 验收标准

1. 造 300 次运行，清理后每 job 保留数 ≤ 上限，目录与 DB 行同步清理；
2. 清理后磁盘占用下降，`freed_bytes` 与实际相符；
3. 人工反馈一条不少，`run_id` 变 NULL；
4. 正在执行的 run 不被删；
5. 告警中心在清理后**依然有数据**（最新 run 保留）；
6. 调度器自动清理（跑一小时以上能观察到），CLI 手动清理也可用；
7. `GET /api/platform/storage` 与 `POST /api/platform/prune` 可用，前端展示正确；
8. 后端测试全绿、`make lint` 全绿、前端测试与类型检查全绿；
9. **端点契约守卫双向绿**（新端点已进清单）。
